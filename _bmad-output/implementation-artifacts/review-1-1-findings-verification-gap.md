# Verification-gap findings — story 1-1
Returned by a context-free reviewer agent.

### `make lint` — the gate this story exists to create — is never executed by any test

- **Changed surface:** the `lint` recipe at `Makefile:12-17` (ruff check, ruff format --check, mypy, lint-imports, env-contract check) and `PYTHON_RUN := $(UV) run --directory $(BACKEND)` at `Makefile:7`.
- **Impacted consumer or site:** the gate contract itself — `AGENTS.md` "Commands (the gates)" and the story's first acceptance criterion ("when `make lint` runs, then it exits 0 having run ruff check, ruff format check, mypy strict on `domain/` and `application/`, `lint-imports`, and the env-contract check"). Every later story's agent is judged by this command, and CI does not exist until story 1.7, so `make lint` is the only thing standing between a weakened gate and a green story.
- **Existing test evidence:** `backend-api/tests/unit/test_makefile.py:25-29` reads only the `.PHONY:` line as text and asserts target *names* appear in it — it never runs them. `test_makefile.py:32-41` does shell out to `make`, but is parametrized over `PENDING_TARGETS` (`test_makefile.py:14-20` = `e2e-api`, `e2e-ui`, `openapi`, `up`, `down`); `lint` and `test` appear only in `DECLARED_TARGETS` (`:22`), which feeds the text assertion. `grep -rn "make lint\|check_env_contract" backend-api/tests scripts Makefile` returns only docstrings, the direct-import/`SCRIPT` path at `test_env_contract.py:13,20`, and `Makefile:17` itself. Nothing executes `make lint` or `make test`.
- **Missing verification:** an assertion that `make lint` exits 0 and that its recipe actually invokes each of the five sub-gates.
- **Demonstration:** delete `Makefile:17`, or drop `--directory $(BACKEND)` from `Makefile:7`. `--directory` is what changes the working directory, and that is the only reason the relative path `../scripts/check_env_contract.py` resolves; without it the AD-20 check stops running. `pytest tests/unit` stays fully green either way — reviewer ran it, 33 passed — because `test_env_contract.py:30-38` invokes the script as `[sys.executable, SCRIPT]` with `cwd=REPO_ROOT`, an invocation shape the Makefile never uses. Removing `ruff format --check` (`Makefile:14`) or the mypy line (`:15`) is likewise invisible to the suite.
- **Consequence:** the gate can be silently narrowed — the exact failure mode the Makefile header comment ("no gate ever passes silently") and the story's "Ask First: any change that would make a gate pass by weakening it" are written to prevent — while `make test` reports success.
- **Suggested test shape:** extend `test_makefile.py` in its existing shell-out style: run `make -n lint` and assert each of the five sub-commands appears in the expanded recipe, and/or run `make lint` and assert exit 0.

### `configure_logging` ships with no test: `LOG_LEVEL` is verified as a parsed string, never as an effect

- **Changed surface:** `backend-api/src/orchestrator/infrastructure/logging.py:15-37` — JSON renderer to stdout (`:30`, `:35`) and the level lookup `logging.getLevelNamesMapping().get(level.upper(), logging.INFO)` (`:20`, `:33`).
- **Impacted consumer or site:** `create_app` calls it at `backend-api/src/orchestrator/main.py:22`, which is exercised on every request in `backend-api/tests/unit/test_healthz.py:16`; and `main()` at `main.py:32-34` for the real process.
- **Existing test evidence:** `grep -rn "configure_logging"` and `grep -rn "structlog"` across the repo return only `logging.py`, `main.py`, and the generated review-prompt artifacts — no test module imports either symbol, and no logging test file exists. The only test that reaches the function is `test_healthz.py:22-33`, which asserts a status code and a JSON body and never captures stdout. `test_settings.py:64` (`assert settings.log_level == "info"`) asserts the value parses, not that it has any effect.
- **Missing verification:** nothing captures an emitted log line and asserts it is JSON on stdout, carries the level and an ISO-UTC timestamp, or that a record below `LOG_LEVEL` is suppressed.
- **Demonstration:** replace `structlog.processors.JSONRenderer()` at `logging.py:30` with `ConsoleRenderer()`, or replace both level lookups (`:20`, `:33`) with a hardcoded `logging.INFO`. Log output becomes non-JSON, or `LOG_LEVEL` becomes inert. Both `test_healthz` tests still pass, `test_settings` still passes, and the full suite stays at 33 passed.
- **Consequence:** the story's own constraint "structlog JSON to stdout at `LOG_LEVEL`; no `print`" ships unverified. Container log consumption breaks silently, and the `run_id`/`path`/`attempt` binding every later story depends on rests on an unpinned configuration.
- **Suggested test shape:** a unit test that calls `configure_logging("warning")`, emits at `info` and `error` through `structlog.get_logger()` with `capsys`, and asserts the captured stdout is one parseable JSON object at `error` only.

### Nothing verifies that `.gitignore` keeps `.env.example` committable (or keeps `.env` out)

- **Changed surface:** `.gitignore:11-15` — `.env`, `.env.*`, then the negation `!.env.example`.
- **Impacted consumer or site:** `scripts/check_env_contract.py:19` (`DEFAULT_ENV_EXAMPLE = REPO_ROOT / ".env.example"`) and `backend-api/tests/unit/conftest.py:16` (`ENV_EXAMPLE = REPO_ROOT / ".env.example"`), whose `env` fixture (used by every `test_settings.py` and `test_healthz.py` test) reads that file. Both reach it by absolute filesystem path — never through git — so both are blind to whether it is tracked.
- **Existing test evidence:** `grep -rn "gitignore\|check-ignore\|check_ignore" backend-api scripts Makefile` returns no hits; no test or gate consults git's ignore rules. The rule works *today*: `git check-ignore -v .env.example` reports `.gitignore:15:!.env.example`, and `git status --porcelain -uall` lists `.env.example` as `??`, so it will be committed.
- **Missing verification:** an assertion that `.env.example` is not ignored, and that a root `.env` / `.env.local` is.
- **Demonstration:** reorder `!.env.example` above `.env.*` (git applies the last matching pattern), or broaden the pattern so the negation stops applying. `.env.example` becomes ignored and `git add -A` silently skips it — no error anywhere. Every test still passes on the author's machine, because the file remains on disk. On a fresh clone — the literal precondition of this story's first two acceptance criteria — `conftest.py:16` yields a nonexistent path, the whole unit suite and `make lint`'s env-contract check die, and the AD-20 contract is gone. The mirror regression is worse: a weakened negation lets a filled `.env` with real secrets be committed, and the only guard the story names for that is the manual `git grep -nE '(ghp_|sk-)[A-Za-z0-9]'` in its Verification section, which nothing automated runs.
- **Consequence:** the configuration contract can silently stop being committed, or a real `.env` can silently start being committed, with a green `make test` in both directions.
- **Suggested test shape:** a test alongside `test_env_contract.py` that shells out to `git check-ignore` (in the same `subprocess.run(..., cwd=REPO_ROOT, check=False)` style already used there) asserting `.env` and `.env.local` are ignored and `.env.example` is not.

### `test_secret_values_never_appear_in_repr` passes while the Postgres password is in the repr

- **Changed surface:** `backend-api/src/orchestrator/infrastructure/settings.py:40` — `database_url: str`, a plain `str` while its six siblings are `SecretStr`. By the committed contract (`.env.example`, `DATABASE_URL=postgresql+psycopg://orchestrator:change-me@postgres:5432/orchestrator`) that value embeds `POSTGRES_PASSWORD`.
- **Impacted consumer or site:** `backend-api/tests/unit/test_settings.py:79-85`, the test standing for `AGENTS.md` hard rule 5 ("Secrets never appear in code, tests, logs, or fixtures") and the story's "Secret redaction" I/O-matrix row; the realistic emitter is the structlog configuration this same story adds (`infrastructure/logging.py`) plus any startup line binding settings.
- **Existing test evidence:** the assertion at `test_settings.py:83-84` loops over `SECRET_VARIABLES` (`test_settings.py:43-50`) — six names, `DATABASE_URL` deliberately not among them — and `:85` only asserts `"**********"` appears *somewhere* in the string. Neither observes an unredacted value outside that six-name list. `test_secrets_are_secret_str` (`:73-76`) is parametrized over the same set.
- **Missing verification:** any assertion that no credential-bearing value from the contract appears in `repr(Settings())`. The check is name-scoped, not value-scoped, so it cannot observe a leak through a field it was not told about.
- **Demonstration:** instantiating `Settings()` from the committed `.env.example` values under the project venv and printing `repr(settings)` renders `database_url='postgresql+psycopg://orchestrator:change-me@postgres:5432/orchestrator'` — `os.environ["POSTGRES_PASSWORD"]` appears verbatim — and `test_secret_values_never_appear_in_repr` passes anyway, because the loop never asks about `DATABASE_URL` and `"**********"` is satisfied by the other six fields. The same holds for any future plain-`str` field carrying a credential.
- **Consequence:** the redaction guarantee is narrower than the name and docstring claim. Any repr or structlog line carrying `Settings` writes the database password to stdout in production, and the test written to prevent exactly that reports green.
- **Suggested test shape:** derive the forbidden values from the contract instead of a hand-kept name list — assert that no value of a credential-bearing `.env.example` variable (including the password segment inside `DATABASE_URL`) appears in `repr(Settings())`, so a new leaking field fails without anyone remembering to extend a set.
