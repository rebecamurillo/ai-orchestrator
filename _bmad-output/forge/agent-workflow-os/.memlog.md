- (crack) Agent validation = 'orchestrator checks output file(s) exist'. This is a liveness check, not a correctness check. It catches crashed/silent agents, not confidently-wrong ones — the actual failure mode in a multi-stage chain.
- (decision) Oracle = Playwright E2E in a prod-like dockerized env with a real DB, as baseline; then human tests the running feature before merging a QA-green PR; fixes go to a new chat session against the epic.
- (crack) Circularity risk: if the E2E tests are generated by an agent from the same PRD/stories, they encode the same misunderstanding and pass. A generated test is a mirror, not an oracle — independence from the artifact is what makes an oracle work.
- (crack) Both real oracles (E2E + human) sit at the END of the chain, after max investment. A wrong premise at idea/PRD stage is only discovered after the full run, so every catch costs a full re-run. Rework economics unexamined.
- (crack) Tension with PoC constraint: 'one docker container with all tooling' vs. needing a prod-like env with a real DB per project/per branch, potentially concurrent. The oracle requirement may already break the single-container assumption.
- (lock) Human gate sits BEFORE code generation: human co-authors/approves user stories + acceptance criteria (AI-assisted). Second human gate is final QA of the running feature before merge. Oracle independence comes from human-approved AC preceding implementation.
- (crack) Two mandatory human gates per feature (AC approval + final QA) make human attention the throughput ceiling, not compute. This undercuts the 'OS across multiple projects' framing: scaling limit is human-minutes and cross-project context switching, not containers.
- (note) QUEUED BRANCH (not yet argued): engine layering — DBOS is already a durable workflow engine (code-first), CNCF Serverless Workflow DSL is declarative, Kestra is a full engine+editor. Proposal implies building a DSL interpreter + a Kestra-like editor + the agent orchestration = three products, only one of which is the actual value.
- (note) QUEUED BRANCH (not yet argued): harness session-id resume is stored in harness-local state inside the container (~/.claude/projects). Container death or the stated v2 multi-container scaling destroys resumability.
- (lock) Throughput model resolved: human gates are ASYNCHRONOUS. Human defines/challenges the need (AI-assisted), then time-slices to other projects while the pipeline runs; returns at epic completion to validate and test. Parallel pipelines amortize the human ceiling.
- (lock) Unit of human return is the EPIC, not the story or the PR.
- (direction) Front-end's PoC job is the async review INBOX (what needs my gate, on which project, with enough context to reload), not the Kestra-style workflow designer. The designer is a separate product and is deferred.
- (kill) REJECTED for PoC: building a CNCF Serverless Workflow DSL interpreter. DBOS is already a durable code-first workflow engine; a declarative DSL layer on top is an interpreter you must write and maintain, and it buys nothing until workflow authors exist outside the core team. Keep YAML definitions with a minimal internal schema; adopt the CNCF DSL when a second consumer justifies it.
- (kill) REJECTED for PoC: Kestra-like visual workflow editor. Workflows are edited as YAML in git for the PoC.
- (kill) REJECTED: 'issue to PR' as a generic first scenario. PoC targets one repo and one ticket class chosen for slow-to-write / fast-to-specify / fast-to-verify.
- (decision) PoC success metric = human-minutes per merged PR vs. the same person writing it by hand. Instrumented in Langfuse from day one. 'It produced a PR' is not the metric.
- (assumption) UNTESTED: that an epic-sized batch of agent work can be validated by a human in materially less time than writing it, once context-reload cost is counted. This is the PoC's central bet.
