AI Agent Workflow OS

Forge session · ai-orchestrator · OptimAI-team · goal: test whether it holds up · mode: attack

The idea survives. Its framing did not: this is not an OS, it is an asynchronous specification-and-verification cockpit. Scope cut, two gates relocated, three build items rejected for the PoC.

What it became

A human defines and challenges the need (AI-assisted). The pipeline runs unattended. The human time-slices to other projects and returns at epic completion to validate and test. The value is not throughput of code — it is moving a senior engineer from writing to specifying and verifying, across parallel pipelines.

Locked

Human-approved acceptance criteria precede code generation

This is the single change that gives the pipeline a real oracle. A test generated from the implementation is a mirror; a test approved before it is independent.

Gates are asynchronous; the unit of return is the epic

Parallelism across projects is what amortizes the human ceiling. Not the story, not the PR — the epic.

Oracle = Playwright E2E, prod-like docker, real DB → then human QA of the running feature

Either it goes green or it does not, and no amount of model confidence changes that.

Killed

Generic “issue → PR” as the first scenario scope

Roughly half of all tickets are faster to write than to specify precisely. The PoC targets one repo, one ticket class: slow-to-write, fast-to-specify, fast-to-verify.

CNCF Serverless Workflow DSL interpreter, for the PoC build

DBOS is already a durable, code-first workflow engine. A declarative layer on top is an interpreter you must write and maintain, and it buys nothing until workflow authors exist outside the core team. Keep YAML with a minimal internal schema; adopt the CNCF DSL when a second consumer justifies it.

Kestra-style visual workflow editor, for the PoC build

A product in its own right. Edit workflow YAML in git until something forces otherwise.

File-existence as “validation” correctness

A liveness check. It catches the crashed agent, never the confidently-wrong one — which is the failure mode that actually reaches the PR.

Hardening required before build

  1. The human signs the executable spec, not the proseIf an agent translates AC → Playwright and nobody reads the spec file, drift re-enters through the translation step. Name which artifact carries the signature.
  2. Invert the escalation triggerPrint-mode agents cannot ask, so they assume and proceed. Escalating on “agent reports blocked” catches the honest agents and misses the dangerous ones. Require every agent to emit open_questions and assumptions; escalate on either.
  3. Label gate strength in the orchestratorEvery step declares liveness / deterministic-oracle / adversarial / human. A stage with no oracle is marked unvalidated, never shown green.
  4. Isolate the E2E environment per runEphemeral DB or schema-per-run, dynamic ports — or serialize runs per repo. Flake that reads as failure destroys trust in the red signal faster than any real bug. Note this already strains the one-container PoC assumption.
  5. Cap the rework loopTwo fix cycles, then hand to a human. A wrong premise otherwise burns budget indefinitely.
  6. The front-end’s PoC job is the review inboxWhat needs my gate, on which project, with enough context to reload cold. The async model depends on this far more than on a workflow designer.
  7. Do not rely on harness session-id resumeThat state is container-local (~/.claude/projects). Container death, or the stated v2 multi-container plan, destroys it. Persist the transcript and the inputs needed to reconstruct a session.

The metric that decides it

Human-minutes per merged PR  vs.  the same person writing it by hand
Instrumented in Langfuse from day one, same trace id. “It produced a PR” is not a result.
If the ratio is ~1.1× on the easy ticket class, it will not survive the hard one.

Weak points that survived scrutiny

The central bet is untested

That an epic-sized batch of agent work can be validated by a human in materially less time than writing it — once cold context-reload cost is counted. Time-slicing away and back is exactly where careful review degrades into rubber-stamping, and nothing in the current design detects a gate that has quietly become a formality.

Cross-repo ownership, never argued

Whoever owns repo #2 owns the PRs this opens — their blame line, their pager. If they must run their own AC gate, then “multiple projects” means multiple humans doing gates: a tool each team installs, not a portfolio system. Different product, different justification for an engine.
