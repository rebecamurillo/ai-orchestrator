# v1 Experience — one operator, one dev loop

`DESIGN.md` still owns colour, type, spacing, shape and component appearance. This document owns **what v1 shows, when, and what it asks of the operator**. Where it disagrees with the 2026-08-25 spine, this one wins for v1 and the reason is stated. Updated 2026-09-02 to the PRD that followed the architecture spine: runs are planned up front, templates compose (`initiative` → `epic` → `story`), credentials are instance settings, and every stop is one row of the PRD's §4.6 Stop table. Updated 2026-09-15 for the mvp-feedback cycle's two UX-gated features: the Run view rework (F3 — §2.2) and the new Step-run detail with full and live logs (F2 — §2.3); deltas 20–26 state every rule this changes. Updated 2026-09-24 for the run-diagram rework (§2.2 *The diagram*, decisions 21a–21c): agents are the nodes, deterministic and checkpoint rows become guardrails, the layout states hierarchy in ranked columns, retries draw as visible calls, and cards drag.

## Attention model (the rule every screen obeys)

The brief asks for "epurated" screens where attention is driven to warnings, blocking steps and running work. Instrument-dark already says *colour is signal only*; v1 narrows the signal set to three hues and one rule:

| Hue | Token | Means | Where it may appear |
|---|---|---|---|
| green `{colors.signal-qa}` | `RUN` | a step is executing right now | chip + token, the "Running" column header |
| amber `{colors.signal-blocked}` | `BLK` `CHK` | the machine stopped and **needs you** — every Stop kind of the PRD §4.6 table; `CHK` for a checkpoint, `BLK` for all others | chip + token, the "Needs you" column header, a 2px left rule on the card / alert banner, an aged wait, the one warning line in a readout |
| red `{colors.signal-infra}` | `ERR` | **Run:** `failed`, terminal (baseline non-zero, `on_fail: fail`, parked 30 days) — nothing will proceed, no Retry. **Step:** the row that errored, which usually sits inside an amber `BLK` run | chip + token, a 2px left rule, the failing command's exit line |
| grey `{colors.text-tertiary}` / `{colors.text-secondary}` | `QUE` `DON` `SKP` `CAN` | planned or queued, done, skipped, cancelled | everything else |

**The rule:** on any card or row, exactly one element carries a signal colour — the reason it needs you. If nothing needs you, the screen has no amber or red pixel: a *declared* human gate on a template node or a future row is the word `human` and a hairline in `{colors.line-strong}`, never amber; a configuration statement (`log_prompt_content` sends source code to Langfuse) is secondary text, never a warning line. Words carry the state (`blocked`, `skipped`, `exit 1`, `unvalidated`, `provisional`); colour only reinforces. The one tolerated pair is a `BLK`/`CHK` card older than 48 h: its token and its age are both amber (they say the same thing).

Dropped from v1: the six per-escalation-type colours (BGT, RWK, INF, CRT). Budget halts and rework are `BLK` with the reason in words.

**Diagram dialect (2026-09-15 — NFR-6 amended for this one surface).** The run diagram is exempt from one-signal-per-surface: every node carries a border colour stating its state — done `{colors.signal-qa}` green · running `{colors.signal-criterion}` blue (the token revived for exactly this) · error `{colors.signal-infra}` red · waiting-for-human `{colors.signal-blocked}` amber · scheduled `{colors.line}` grey. Two hue meanings deliberately differ from the rest of the app **on the diagram only**: green means *done* (everywhere else it means *executing now*) and blue exists (everywhere else it doesn't). `SKP` and `CAN` nodes carry the faint `{colors.line}` grey border and the word token only — skipped is never green, on the diagram as everywhere (the frozen convention). Group boxes are nodes: a box's border carries its AD-15 aggregate colour, so the path to a stop is amber at every level. *(2026-09-24: in the v3 ranked-column layout those group boxes are the **epic** and **story** nodes of ranks 1 and 2 — the aggregate rule and the amber-at-every-level consequence are unchanged; a guardrail-strip entry carries the same dialect as a 4px dot beside its word.)* Colour is never alone: the word token sits beside every border, and the token stays the authoritative state. This dialect amends DESIGN.md's "the left border is the only place a signal colour extends beyond 7px" rule on this surface only. Off the diagram, the attention model above is unchanged.

## Information architecture

| # | Surface | Route | Purpose |
|---|---|---|---|
| 1 | Login | `/login` | Enter the operator token. |
| 2 | Workflows (home) | `/` | Board of runs by status. Where is everything; what needs me. |
| 2.1 | New workflow | `/workflows/new` | Bind a template's inputs, see pre-flight and the whole plan, start. |
| 2.2 | Run detail | `/workflows/:runId` | One run: stop zone when it needs you, the diagram as the centerpiece, stories, cost, artifacts (modal), gate record / steps / session tabs. The `?view=diagram` surface was retired 2026-09-15; its redirect and the DIAGRAM/DETAIL toggle stub are **removed** 2026-09-24 — the route takes no `view` parameter. |
| 2.3 | Step-run detail | `/workflows/:runId/steps/:path` | One planned step: every attempt with its dispatch and retry prompts, exit code, duration, cost — and the full log, live while running. |
| 3 | Projects | `/projects`, `/projects/:id` | Projects, context, repositories, method readiness, trajectories export. |
| 3.1 | New project | `/projects/new` | Form + live clone check. |
| 4 | Runs | `/runs` | Every attempt: engine queue (top) and history (below). |
| 5 | Templates | `/templates/:name/:version` | YAML editor + rendered diagram + inputs; versions and callers. |

No new route: a `repo-init` run and a harness readiness run are ordinary runs on the board and in run detail.

**Shell.** Fixed 172px rail: *Workflows* (count + "n need you" in amber when n>0), *Runs*; Configure: *Projects*, *Templates*. Footer readout: `2 running · 1 queued / 2 need you / updated hh:mm:ss · refresh`. No notifications surface — "Needs you" is a column and a rail count. **A failed fetch** replaces the surface with a full-surface readout: the failed request (method, path, status) in a command block and a *Retry* control; nothing else moves.

**Depth.** Three levels, no more: board → run detail → step-run detail (2026-09-15; was two). New workflow is a page, not a modal (up to eleven fields plus a pre-flight readout and the plan, must be bookmarkable and survive a reload). Two modals exist: the destructive confirm for *Cancel run*, and the artifact viewer/editor (§2.2 — 2026-09-15). The step-run detail's helper drawer (§2.3) is a side panel, not a modal — the page behind it stays live.

**Refresh.** Polling every 5 s while anything is `RUN`, 30 s otherwise; the footer states the last update. Content never moves under the cursor: a card changing column is a state swap on the next poll, not an animation. One exception: a followed log tail (§2.3), where appending is the point — the follow/pause control governs it.

## Naming rule: label and path

Every planned step has a **path** (`epics[0].stories[3].build`) and a **label** (`epic 1 · story 4-1 · build`). Detail contexts that never truncate — the Steps table, the gate record, the Runs history — print the path. Single-line contexts — cards, the LIST row, the Stories strip, the diagram footer, banners — print the label. A step is never named two ways in one component; a detail header may pair them — label as the crumb or eyebrow, path as the title (§2.3 does).

## Operator workflow (Flow.dc.html)

1. **Login** — token once per 30 days.
2. **Projects → New project** — name, context text, context file paths, agent env vars (masked after save), `log_prompt_content` switch with its plain statement, one or more repositories with `default_branch`, package manager, `test_globs` (default shown: `tests/**`, `**/*.test.*`, `**/*.spec.*`), `install_command`, `quality_gate_command` (optional), `unit_test_command` (optional). No token field: the form states that the GitHub token and the gateway key are instance settings. **Save runs the clone check** per repository: `git ls-remote`, shallow clone, default branch exists, method version found in `_bmad/`. A failing repository does not block save: its row reads `failed` with the verbatim git output and a one-line fix (for a token without access: "the instance's GitHub token has no access to this repository"), and no run can start on it until the check passes; *re-run check* sits on the row. A repository whose method is `missing` or `outdated` offers *Initialise repository*.
3. **Workflows → New workflow** — template (`initiative` latest pre-selected; `epic`, `repo-init`; `story` is not offered), project, repository, base branch, then the inputs that template declares (`initiative`: initiative folder; `epic`: working branch + spec folder), harness (probe-gated: the row states the live probe result or its specific failure reason; the readiness badge informs, it does not gate), model (a select over the probed harness's models, never free text), budget (optional; without one the run is `tracked, no cap`), *re-review done stories* (off), manual estimate (optional). **Pre-flight** re-runs on every change: origin reachable, base branch exists, each branch the plan will check out exists / will be created / is held by another run, `epics.yaml` parses (epics, branches, spec folders), every `stories.yaml` parses (count, id rule), checkpoints declared (warning, never blocking), `SPEC.md` in every spec folder, harness probe passes, `_bmad/` at the pinned version (fix: `run Initialise repository and merge its branch`), existing story files with statuses, clone check not failed. A red line disables *Start run* and states the fix. **What will run** is the whole plan. *Start run* persists the plan and enqueues: it starts immediately if the branch is free, else queues behind the run holding it — the button's note names that run; an active run elsewhere on the same repository raises the consent warning with the facts (which run, which branch, which spec folder — `this can lead to merge conflicts`) and requires explicit confirmation. *Save* beside it stores the planned run without enqueueing; a saved run may declare `after: {run_id}` and enqueues when that run reaches `done`.
4. **Workflows board** — walk away. Come back: green is running, amber needs you, red failed. The card says the label of the current step (`epic 1 · story 3-2 · build · claude · 00h 42m`) and the progress (`1/2 epics · 5/8 stories · 1 link`). Open a card: the diagram is the centerpiece of the run view — what ran, where it is, what is scheduled, one glance. Click the box that is moving (or stuck) to open its step and read the log as it writes.
5. **Run detail** — the banner names the Stop and the body follows the Stop table below: for a blocked story the question at 14px, an **Answer** box, *Resume with answer*; for a checkpoint the story spec file inline with *Continue* and *Reject with a reason*; for an errored step the failing output with *Retry*. Every stop also offers the skips it admits, *Cancel run*, and — while parked — inline editing of the spec folder files. Secondary: the resume command block (Claude, Codex; it execs into the `backend-api` container, and while a terminal session is in progress the other actions are disabled until *Release*, or until the server sees the story `done` and resumes on its own).
6. **Done** — `DON` card with `2/2 epics · 8/8 stories · 2 links`; the summary lists one compare link per epic and any skipped stories or epics beside them. Opening the pull request and merging are the human's, in GitHub.

## Screens

### 1 · Login (`Login.dc.html`)
Centered 400px panel: brand, `ACCESS TOKEN` input, *Enter*, one hint line (where the token comes from, cookie lifetime). Rejection replaces the hint with `token rejected — n attempts left` in red; after the fifth failure the line reads `too many attempts — try again in 15 min` and the input is disabled (COULD).

### 2 · Workflows board (`Main.dc.html`)
- Bar: title, count readout (`7 runs · 2 need you · oldest wait 2d 04h`), filter, project segmented filter (query string), BOARD/LIST toggle, *+ New workflow*.
- Five equal columns, never collapsing: **Queued · Running · Needs you · Done · Failed**. Header counts. The Running header is green, the Needs-you header amber; all others grey. `cancelled` runs sit under Failed with the grey `CAN` token and the word `cancelled`.
- Card, fixed order: chip + token (+ harness name right, tertiary) · current branch · project · repository · current or last step **label** · progress `n/n epics · m/m stories · k links` (the epic figure omitted for an `epic` run; a `repo-init` or readiness run shows `repo-init` / `readiness` in place of progress) · template name and version · age. Blocked/failed cards carry the 2px left rule. Aged waits (>48h) turn the age amber.
- Cards are not draggable; status is computed. Whole card → run detail.
- Empty column: `—` placeholder, header count 0. Empty board: `NOTHING RUNNING` + what is queued + link to New workflow. First run: `NOTHING REGISTERED` → Projects.
- LIST toggle: the same data as record rows (token · project · repository · branch · step label · progress · age) for when the board has more than ~20 cards.

### 2.1 · New workflow (`NewWorkflow.dc.html`)
Two columns: form (left, 190px labels) and **Pre-flight** + **What will run** (right). The form is template-dependent: choosing a template swaps the input rows below *base branch* for the ones it declares. The harness row is a list, one line per harness: name, the live probe result in words (`ok`, or the specific reason — `not logged in`, `gateway unreachable`), and the readiness badge with its last run time and a *run readiness* link (a diagnostic; it informs, it does not gate). A harness whose probe fails cannot be selected — the line states the reason, never a bare disabled flag; probe success loads the **model** select (the probed harness's models, never free text). Pre-flight lines are `ok / ! / x / —` words in the first column, never icons. "What will run" is the plan as a dense table — `path · kind · gate` per row, loops expanded to the parsed epic and story counts, the first row `plan · plan.check`, already-done stories as `skipped · already done` unless *re-review* is on — the operator sees exactly the rows the run will execute. Decision bar under the form: *Start run* (primary), *Save* (stores the planned run without enqueueing; with `after: {run_id}` it waits with `waiting for run {x}`), *Cancel*, one note about queueing that names the holding run; the shared-repository consent warning renders here when another run holds the repository on a different branch.

### 2.2 · Run detail (reworked 2026-09-15 — F3; artboard: [mockups/RunDetail-v2.html](mockups/RunDetail-v2.html) — `RunDetail.dc.html` superseded. **The diagram sub-section is reworked again 2026-09-24 — v3, artboard [mockups/RunDiagram-v3.html](mockups/RunDiagram-v3.html).**)

Top to bottom: header → **top zone** → **diagram** (the centerpiece) with the summary column on its right → one **tabbed region**. The top zone renders by run state: needs-you or failed — the full stop body below; done — the one-line summary; cancelled — one grey line; while the run is queued or running it does not exist and the diagram sits directly under the header. The layout breathes by state.

- **Header:** crumb, chip + token + branch + age of the current state, meta line unabridged (project · repository · base · initiative or spec folder · template version · harness · **model** · started · worktree path) — the model the run dispatches with is always stated (item 11: it was invisible). Right-aligned: progress `n/n epics · m/m stories · k links` + spend.
- **Stop zone**, above the diagram: the alert banner (token, the Stop's reason text verbatim — `verify failed 2/2`, `protected path modified: tests/api/test_runs.py`, `budget $41.20 / $40.00`, right-aligned progress + spend) and directly under it the full Stop body and actions per the table below. Resolving a stop never requires a scroll or a tab.
- **Summary column** (right of the diagram): **Stories** strip (`n/m` per epic, one cell per story labelled by id: done filled, current amber, future hollow, skipped struck) → **Cost & trace** kv (spent/budget ratio — `tracked, no cap` when the run has no budget — tokens, wall-clock, your active time, Langfuse trace link, the epic compare links, branch link; a figure not yet confirmed by the gateway carries the word `provisional`) → **Artifacts** tree at spec-folder scope with changed-since-last-opened chips; a file opens in the artifact modal.
- **Artifact modal:** opens in reader view — Markdown rendered, YAML and code syntax-highlighted, a `RENDERED · SOURCE · RAW` toggle, *download*. While the run is parked and no terminal session is in progress, *Edit* switches the same modal to the editor (Markdown, YAML) with *Save* — the hint under it says `saved as commit "spec: operator edit (orchestrator)" on {branch}`. `stories.yaml` and `epics.yaml` open read-only with the line `planned at {sha} — start a new run to change the list`. A failing *Save* (commit rejected, branch moved) prints the git output verbatim in the modal and keeps the buffer — the clone-check pattern.
- **Tabbed region** (bottom, full width, the page's last element): **GATE RECORD** (default) · **STEPS** · **SESSION**.
  - *Gate record*: append-only; one line per event: time · path · event · actor · text; events are the Stop kinds, the signals and `start / done / failed / cancelled`.
  - *Steps*: the dense table (`path · kind · gate · status · time · harness · cost`), every planned row present from the start, `planned` rows as `QUE`, the current row promoted to primary text, a row with more than one attempt showing the latest and `· 3 attempts`. Gate column prints `liveness / deterministic / human / unvalidated` as words; status prints `skipped · already done`, `skipped · skipped by operator`, `skipped — no quality_gate_command` where it applies; nothing in these two columns is ever green. Every row links to its step-run detail (§2.3).
  - *Session*: **Or continue in the session** — the resume command block (Claude, Codex; it execs into the `backend-api` container), copy control, session lifetime; hidden for `local`.

**The diagram** (embedded; the standalone `?view=diagram` surface is retired and redirects here):

*(Reworked 2026-09-24 — v3, ranked-column hierarchy. Operator-authorized revision of AD-15 and of this section's 2026-09-15 text; artboard: [mockups/RunDiagram-v3.html](mockups/RunDiagram-v3.html). The four bullets this replaces — a node per planned row, dagre+SVG read-only rendering, and click-to-navigate on a leaf — are retired. The **template** diagram (§5) is untouched and keeps dagre+SVG.)*

- **What is a node.** Only **agent** steps are nodes (`RunNodeOut.agent === true`), plus the three structural nodes: the run root, one epic node per `epics[i]` group, one story node per `epics[i].stories[j]` group. **Deterministic and `checkpoint` rows are not nodes** — they render as the guardrail strip of the epic or story that owns them. Every planned row, node or not, stays present and addressable in the STEPS tab; the diagram narrows what it *draws*, never what the run *has*.
- **Layout — ranked columns, left to right.** Depth is a column, not a nesting box. Four ranks under `{typography.column-head}` heads `RUN · EPICS · STORIES + EPIC AGENTS · AGENTS`: **R0** the run root · **R1** one node per epic · **R2** the epic's children in plan order — its own agent steps (`spec-gate`, `gen-e2e`, `retro`) *and* its story nodes, interleaved as the plan orders them · **R3** the agent step(s) inside a story (`build`). Siblings stack vertically in **spec order** (`epics.yaml`, then `stories.yaml`). Connectors are orthogonal hairlines (`{colors.line-strong}`) drawn behind the cards, parent rank to child rank only.
- **Hierarchy, not execution.** The layout states the shape of the work, not the order it ran: there are **no edges between sibling stories**, because there is no step-level dependency to draw — within one Run the plan is a dense `seq` chain and `parallel` is a rejected template key. Sequence is conveyed by vertical reading order. The cross-Run initiative DAG (`depends_on`, `after_run_ids`) is **not** on this surface.
- **Guardrail strip.** A thin row at the foot of an epic or story node, above a `{colors.line}` hairline: `{typography.micro}` in `{colors.text-tertiary}`, one 4px status dot + the step word per entry, joined by ` · ` — story: `sync · verify · commit-guard`; epic: `branch · setup · baseline · commit-e2e · e2e · +3` (five entries, then `+k`). Information only — not clickable, not connected, and deliberately the quietest thing on the card. Guardrails say the process is guarded; they are never the main event.
- **Retries are visible calls.** Each failed attempt of an agent step draws as a small chip in an **attempts gutter** right of its agent card — `try n` over `failed` (and `exit {code}` for the latest failed attempt, the only one whose code is on the wire) — with a **dashed curved edge** in `{colors.signal-infra}` looping back into the card, labelled `retry`. Failed-attempt count is derived from `StepRowOut.attempts`: `attempts − 1` when the row ended `done | skipped`, `attempts` otherwise. A step with one attempt has no gutter.
- **Colour:** the diagram dialect (attention model, above) — border + token per node: done green, running blue, error red, waiting-for-human amber, scheduled grey. The word token is authoritative; colour reinforces.
- **Node:** `{typography.row-title}` title, `{typography.eyebrow}` kind (`epic`, `story`, `agent` — or the word `now` in `{colors.accent}` on the current step), chip + token right-aligned, `{typography.meta}` detail. An agent node's meta states `{harness} · {model}` and its duration; an epic node's states `k/n steps`; the root's states `n epics · m stories`. No node carries more than one border colour.
- **Click grammar (revised).** The card **body is a drag handle**, not a link. Navigation is one explicit control: an **`Open step` CTA** (`{typography.control}`, `{colors.line-strong}` border) inside every agent node, which goes to the step-run detail (§2.3). An epic or story node carries a caret that expands or collapses its children in place, one level per click. Nodes on the path to the current step (running or stopped) render expanded; every other epic starts collapsed.
- **Drag is session-only.** Any card can be dragged anywhere on the canvas; positions are **not persisted** and the computed tree returns on reload — so a run whose plan grows mid-flight never leaves orphaned cards. A `reset layout` control restores the computed tree without a reload, beside `fit` and the zoom readout in the bar above the canvas.
- **Footer readout** under the tree: `step 15 of 22 · epic 1 · story 4-1 · build · blocked 2d 04h · 5/8 stories`.
- **One blue node, and the ancestors that hold it** *(ratified 2026-09-24 — this resolves a contradiction between this section's "`RUN` — one blue node" and AD-15's group-status rule, which makes every ancestor of a running step `running` too)*. The **blue border belongs to the current step alone**. An epic or story node whose aggregate is `running` carries a `{colors.line-strong}` border and the blue `RUN` **word token** — the token still states the aggregate truthfully, the border does not repeat it. So a diagram of a healthy run has exactly one blue rectangle on it, and it is the thing that is executing. The same rule does **not** apply to a stop: an `ERR`/`BLK`/`CHK` aggregate keeps its coloured border at every level, because the path to a stop must be findable by colour from the root down.
- **States:** `RUN` — one blue node (its ancestors expanded, bordered `{colors.line-strong}` and tokened `RUN`). `BLK`/`CHK` — the stopped node amber; the stop zone above says why; a `checkpoint` row that is *itself* the stop shows amber on the node that owns its guardrail strip, and the strip entry carries the amber dot. `DON` — done nodes green, skipped nodes faint grey (`SKP` — never green), each epic node carrying its compare link. `CAN` — no group aggregates; the root reads `CAN`. Queued — every node grey, root says `waiting: …`. Empty plan — the words `no steps planned`, no canvas. Loading — the skeleton block, no spinner. A failed graph fetch — the full-surface failed-request readout with its retry control (the one-polling-loop rule), never a half-drawn tree. A poll updates statuses **in place**: nodes never move, re-collapse, or lose a drag position under the cursor.
- **Accessibility.** Every node is a labelled group announcing `{label} · {status word}`; the `Open step` CTA and the expand caret are real buttons (the caret carries `aria-expanded`), both reachable by Tab in reading order. Colour is never the only carrier — the word token and the guardrail step words are text. Arrow keys pan the canvas; drag is a convenience, never the only way to reach anything.
- **Stop bodies and actions** (the PRD §4.6 table, rendered in the stop zone):

| Stop (banner) | Body in place of the Question | Primary | Also offered |
|---|---|---|---|
| `blocked` | the whole `## Auto Run Result`, agent attribution eyebrow, amber rule; **Answer** textarea with the hint stating the mechanism (archived to `stories/.answers/{id}-attempt-{n}.md`, story re-planned with the answer; edit `SPEC.md` on the branch when the gap is in the spec) | *Resume with answer* | *Skip story* · *Skip epic* · *Cancel run* |
| `spec checkpoint` / `done checkpoint` | the planned story file inline (spec) or the story's summary (done) | *Continue* | *Reject with a reason* (spec only; a textarea, same mechanism as Answer) · *Skip story* · *Skip epic* · *Cancel run* |
| `verify failed 2/2`, `re-baseline failed after skip` | the failing command and its last 40 lines in a command block | *Retry* | *Skip story* · *Skip epic* · *Cancel run* |
| `budget {spent} / {budget}` | the cost kv promoted; a numeric *new budget* field | *Raise budget* | *Cancel run* |
| `stalled {path}: no activity for {n} min` (agent steps, the default) · `timeout {path} after {n} min` (`shell`/`git.*`, or a declared `timeout_min`) | the last 40 lines of the attempt log | *Retry* | *Skip story* · *Skip epic* · *Cancel run* |
| `push rejected`, `sync: branch diverged` | the git output; a line: `resolve on the remote, then Retry — Retry fetches first` | *Retry* | *Skip epic* · *Cancel run* |
| `protected path modified: {files}` | the file list with `+ − ~` per file and a diff link into the artifacts tree; a line naming what *Accept* does | *Accept changes* | *Retry* · *Skip story* · *Skip epic* · *Cancel run* |
| `harness misconfigured: …`, `no story file`, `ambiguous story file`, `unexpected status: …`, `harness exit {code}`, `gateway unreachable` | the condition, the file list where there is one, the log tail; **no Answer box** | *Retry* | *Skip story* · *Skip epic* · *Cancel run* |
| `plan stale: {file}` | the diff of the list file between the plan commit and the branch head | *Continue on the recorded plan* | *Cancel run* (and `start a new run` link) |
| `internal: {error}` | the exception line and log tail | *Retry* | *Skip story* · *Skip epic* · *Cancel run* |
| `run {x} ended {status}` | the predecessor's end (`failed` / `cancelled`), linked to that run's card; a line stating the dependent was not auto-started | *Start anyway* (Continue) | *Cancel run* |

- Other states: `RUN` — no stop zone; the diagram's one blue box says where the run is. `ERR` (run `failed`) — stop zone red; the failing command and its last 40 lines; no action but `start a new run` (a link to New workflow pre-filled) — failed runs are terminal. `DON` — the stop zone's place holds a one-line summary: progress, one compare link per epic, skipped stories and epics listed by id. `CAN` — grey banner, `cancelled by operator at …`.
- **Terminal session in progress** — the reason renders twice: in the SESSION tab under the command block, and in the stop zone beside the disabled actions together with the *Release* control: `terminal session in progress · Answer, Continue, Skip and Retry disabled until Release — the run resumes by itself when the story file is done and the tree is clean`. The artifact modal's *Edit* is disabled for the same reason, same line.

### 2.3 · Step-run detail (new 2026-09-15 — F2; artboard: [mockups/StepRunDetail.html](mockups/StepRunDetail.html))

The answer to "it failed, why?" without a shell into the container. One planned step of one run — every attempt, its prompts, and the full log, live while it runs. Reached from an agent node's *Open step* CTA on the diagram (2026-09-24: the card body no longer navigates — it is a drag handle), a Steps-tab row, or a Runs-history row; bookmarkable; survives reload mid-tail. A deterministic or `checkpoint` row has no diagram node and is reached from its Steps-tab row — the guardrail strip names it but does not link.

- **Route:** `/workflows/:runId/steps/:path` with the path in **dot-index form** — `epics.0.stories.3.build` — so nothing needs URL-encoding; the page itself prints the canonical bracket path.
- **Header:** crumb back to the run, then the step: label (`epic 1 · story 4-1 · build`), the **path** in full (this is a detail context — path, per the naming rule), chip + token, kind and gate as words, harness where one applies.
- **Dispatch context:** `with_resolved` as a kv block — every value the step was dispatched with, resolved.
- **Attempts**, newest first, the latest selected: `#n · status · exit {code} · duration · cost · session {id}`. The harness **session id is printed on the row in full with a *copy* control** — it is the handle for reaching that agent conversation again. Two controls sit on every agent attempt row, each opening the helper drawer (below): ***prompt · result*** — the attempt's **prompt** (the dispatch prompt and, for a retry, the exact `retry.prompt` the template declared — item 15: the retry prompt is a visible, maintained part of the workflow definition; F2 is its display side) and its **result** (what the agent reported back, verbatim: the status it wrote to the story file and the message with it — the `## Auto Run Result` block for a blocked attempt; the error and its explanation for a failed one; the summary for a done one; `— running` while in flight) — and ***reach agent***, the resume instructions for that session. Non-agent rows (`shell`, `git.*`) carry no harness, session or token figures and no drawer controls; their command line stands in place of the prompt and their exit line in place of the result — the log is their full account.
- **Helper drawer** — a panel that opens from the right edge and closes with one control; never a modal: the page behind it stays live and the log keeps following under it. One drawer, two contents, opened from the attempt rows: (a) ***prompt · result*** — the attempt's prompts and result as above, each block with a *copy* control; (b) ***reach agent*** — numbered instructions for resuming that attempt's session: the command block (it execs into the `backend-api` container and runs the harness's resume command bound to that session id; *copy*), the session lifetime, and the standing rule restated in place: while a terminal session is in progress on the run's current stop, *Answer*, *Continue*, *Skip* and *Retry* are disabled until *Release* — the run resumes by itself when the story file is done and the tree is clean. A past session opens for interrogation; only the current stop's session moves the run. Opening or closing the drawer changes nothing else on the page.
- **Log:** the selected attempt's full log — every step kind, deterministic and agent alike — in an inset command block that fills the remaining viewport height: the log is the page's main element. Cursor-paged. While the attempt is running the log **follows**: new lines append on the poll interval, the view keeps the tail in sight, and the line above it reads `following · updated hh:mm:ss`; scrolling up pauses following, a *follow* control resumes it — following is on by default for a running attempt. When the attempt ends mid-follow, following stops with the final line in view and the token updates on the next poll. *download raw* serves the file unrendered. A log no longer on disk reads `log no longer on disk` — a words-only line, never an error surface. Delivery is through the web-client proxy (AD-1); the browser never reaches the log volume.
- **States:** attempt running — token `RUN`, log following. Attempt done — `DON`, static log, no follow control. Attempt failed — `ERR`; the exit line is the one red line in the readout. Step `planned`/`queued` — the page exists before anything ran: dispatch context and `no attempts yet`. Skipped step — dispatch context and the skip reason in words (`skipped · already done`, `skipped · skipped by operator`); no attempts section. Blocked or checkpointed step — the stopped attempt's row states the stop reason and links `answer on the run` back to the run detail; the actions live in the stop zone, never here.

## State vocabulary

| Token | Run | Step |
|---|---|---|
| `QUE` | enqueued, or waiting for a branch partition or a concurrency slot, or saved (`saved — not started`, `waiting for run {x}`) | `planned` (predecessor not done) or `queued` (next to run) — the word says which on hover / in the table |
| `RUN` | a step is executing | executing |
| `BLK` | any Stop of §4.6 except a checkpoint: blocked, verify failed, budget, timeout, push rejected / sync diverged, protected path, misconfigured, plan stale, internal | the step that stopped (`blocked` or `error`) |
