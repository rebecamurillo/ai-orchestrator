- (decision) Tree shape: RANKED COLUMNS. Depth is a column, not nesting. R0 run | R1 epic | R2 story + epic-level agent (spec-gate, gen-e2e, retro) | R3 story agent (build). Siblings stack vertically in spec order. Preserves EXPERIENCE-v1 decision 18 (one orientation, left to right).
- (decision) Retry affordance: RETRY LOOP EDGE. Each failed attempt of an agent step draws as a small chip node in an attempts gutter right of the agent card, with a dashed curved edge labelled 'retry' looping back into the card. The failure is a visible call, not a counter.
- (decision) Drag: SESSION ONLY. Cards drag freely; positions are not persisted and reset to the computed tree on reload. Nothing is stored, and a run whose plan grows mid-flight never leaves orphaned cards. A 'reset layout' control restores the computed tree without a reload.
- (decision) Collapse default: PATH TO THE CURRENT STEP. The epic and story containing the running or stopped step open on load; every other epic is collapsed to its card. Unchanged from EXPERIENCE-v1 2.2.
- (decision) Structure confirmed from templates/: an epic carries three agent steps of its own outside its story loop (spec-gate before, gen-e2e and retro after) plus eight deterministic rows; a story carries exactly one agent (build) plus sync, verify, commit-guard. The tree therefore has real branching at R2.
- (assumption) COLLISION between the retry-loop-edge decision and the client-join decision: StepRowOut exposes attempts as an INTEGER count plus latest only — there is no per-attempt history on /detail, and retry_count/redispatch_count are not on the wire. Per-attempt exit codes exist only on GET /runs/{id}/steps/{path}. Resolution without a backend change: failed-attempt count is DERIVED — attempts-1 when the row ended done or skipped, attempts otherwise — so retry chips render as 'try n / failed' and only the latest failed attempt can state an exit code.
- (event) Gap batch resolved: tree shape, retry affordance, drag persistence, collapse default.
- (decision) Ratified: the BLUE BORDER belongs to the current step ALONE. An epic or story node whose aggregate is running carries a line-strong border plus the blue RUN word token — the token states the aggregate, the border does not repeat it. A healthy run therefore shows exactly one blue rectangle, and it is the thing executing. Stops are the exception: ERR/BLK/CHK aggregates keep their coloured border at every level so the path to a stop stays findable by colour from the root down. Resolves a latent contradiction between EXPERIENCE-v1 2.2 ('RUN — one blue node') and AD-15's group-status rule.
