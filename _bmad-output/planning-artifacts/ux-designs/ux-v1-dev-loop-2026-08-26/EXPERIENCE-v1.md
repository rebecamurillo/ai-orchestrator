# v1 Experience — one operator, one dev loop

`DESIGN.md` still owns colour, type, spacing, shape and component appearance. This document owns **what v1 shows, when, and what it asks of the operator**. Where it disagrees with the 2026-08-25 spine, this one wins for v1 and the reason is stated.

## Attention model (the rule every screen obeys)

The brief asks for "epurated" screens where attention is driven to warnings, blocking steps and running work. Instrument-dark already says *colour is signal only*; v1 narrows the signal set to three hues and one rule:

| Hue | Token | Means | Where it may appear |
|---|---|---|---|
| green `{colors.signal-qa}` | `RUN` | a step is executing right now | chip + token, the "Running" column header |
| amber `{colors.signal-blocked}` | `BLK` `CHK` | the machine stopped and **needs you** (agent blocked, checkpoint, budget halt) | chip + token, the "Needs you" column header, a 2px left rule on the card / alert banner, an aged wait, the one warning line in a readout |
| red `{colors.signal-infra}` | `ERR` | a step failed and nothing will proceed (baseline red, retries exhausted, clone failed) | chip + token, a 2px left rule, the failing command's exit line |
| grey `{colors.text-tertiary}` / `{colors.text-secondary}` | `QUE` `DON` `SKP` | queued, done, skipped | everything else |

**The rule:** on any card or row, exactly one element carries a signal colour — the reason it needs you. If nothing needs you, the screen has no amber or red pixel. Words carry the state (`blocked`, `skipped`, `exit 1`, `unvalidated`); colour only reinforces.

Dropped from v1: the six per-escalation-type colours (BGT, RWK, INF, CRT). Budget halts and rework are `BLK` with the reason in words.

## Information architecture

| # | Surface | Route | Purpose |
|---|---|---|---|
| 1 | Login | `/login` | Enter the operator token. |
| 2 | Workflows (home) | `/` | Board of runs by status. Where is everything; what needs me. |
| 2.1 | New workflow | `/workflows/new` | Bind a template's variables, see pre-flight, start. |
| 2.2 | Run detail | `/workflows/:runId` | One run: alert, question + answer, steps, stories, artifacts, cost, actions. |
| 2.3 | Run diagram | `/workflows/:runId?view=diagram` | The same run as a left-to-right tree with a status token per node: what ran, where it is, what is scheduled. |
| 3 | Projects | `/projects`, `/projects/:id` | Projects, context, repositories, credentials. |
| 3.1 | New project | `/projects/new` | Form + live clone check. |
| 4 | Runs | `/runs` | Every step: DBOS queue (top) and history (below). |
| 5 | Templates | `/templates/:name/:version` | YAML editor + rendered diagram + inputs; versions. |

**Shell.** Fixed 172px rail: *Workflows* (count + "n need you" in amber when n>0), *Runs*; Configure: *Projects*, *Templates*. Footer readout: `2 running · 1 queued / 2 need you / updated hh:mm:ss · refresh`. No notifications surface — "Needs you" is a column and a rail count.

**Depth.** Board → run detail is the maximum. New workflow is a page, not a modal (eight fields plus a pre-flight readout, must be bookmarkable and survive a reload). The only modal is the destructive confirm for *Cancel run*.

**Refresh.** Polling every 5 s while anything is `RUN`, 30 s otherwise; the footer states the last update. Content never moves under the cursor: a card changing column is a state swap on the next poll, not an animation.

## Operator workflow (Flow.dc.html)

1. **Login** — token once per 30 days.
2. **Projects → New project** — name, context text, context file paths, GitHub token, agent env vars, one or more repositories with `default_branch`, package manager, `quality_gate_command` (optional), `unit_test_command` (optional). **Save runs the clone check** per repository: `git ls-remote`, shallow clone, default branch exists. A failing repository blocks save with the verbatim git output. The form keeps every value.
3. **Workflows → New workflow** — template (latest version pre-selected), project, repository, base branch, working branch, spec folder, epics file (optional), stories file, harness (`claude | codex | local`), model (harness default), budget, manual estimate (optional). **Pre-flight** re-runs on every change: origin reachable, base branch exists, working branch exists/will be created, `stories.yaml` parses (count, ids prefix-free), checkpoints declared (warning, never blocking), `SPEC.md` found, epics file found, harness available and project key present. A red line disables *Start run* and states the fix. *Start run* enqueues: it starts immediately if the repository is free, else queues behind the run holding it — the button's note says which.
4. **Workflows board** — walk away. Come back: green is running, amber needs you, red failed. The card says the story and step (`story 3-2 · build · claude · 00h 42m`) and the story count (`5/8`). Open a card and flip to **DIAGRAM** to see the whole run as a tree — what ran, where it is, what is scheduled.
5. **Run detail** — for `BLK`: the question at 14px, an **Answer** box, *Resume with answer*, *Skip story*, *Cancel run*; secondary: the resume command block (Claude, Codex; it execs into the container, and while a terminal session is in progress the other actions are disabled until *Release*). For `CHK`: the story spec file opened inline, *Continue* / *Cancel run*. For `ERR`: the failing command and its output, *Retry step* / *Cancel run*.
6. **Done** — `DON` card with `n/n stories · pushed · PR #` link. Merge is the human's, in GitHub.

## Screens

### 1 · Login (`Login.dc.html`)
Centered 400px panel: brand, `ACCESS TOKEN` input, *Enter*, one hint line (where the token comes from, cookie lifetime). Rejection replaces the hint with `token rejected — n attempts left` in red. Nothing else on the page.

### 2 · Workflows board (`Main.dc.html`)
- Bar: title, count readout (`7 runs · 2 need you · oldest wait 2d 04h`), filter, project segmented filter (query string), BOARD/LIST toggle, *+ New workflow*.
- Five equal columns, never collapsing: **Queued · Running · Needs you · Done · Failed**. Header counts. The Running header is green, the Needs-you header amber; all others grey.
- Card, fixed order: chip + token (+ harness name right, tertiary) · working branch · project · repository · current or last step line · `n/m stories` · template version · age. Blocked/failed cards carry the 2px left rule. Aged waits (>48h) turn the age amber.
- Cards are not draggable; status is computed. Whole card → run detail.
- Empty column: `—` placeholder, header count 0. Empty board: `NOTHING RUNNING` + what is queued + link to New workflow. First run: `NOTHING REGISTERED` → Projects.
- LIST toggle: the same data as record rows (token · project · repository · branch · step · age) for when the board has more than ~20 cards.

### 2.1 · New workflow (`NewWorkflow.dc.html`)
Two columns: form (left, 190px labels) and **Pre-flight** + **What will run** (right). Pre-flight lines are `ok / ! / x / —` words in the first column, never icons. "What will run" is the template's step list with the loop expanded to the story count — the operator sees the plan without a gate ceremony. Decision bar under the form: *Start run* (primary), *Cancel*, one note about queueing.

### 2.2 · Run detail (`RunDetail.dc.html`)
- Header: crumb, chip + token + branch + age of the current state, meta line unabridged (project · repository · base · spec folder · template version · harness · started · worktree path).
- **Alert banner** only when the run needs you or failed: token, one sentence, right-aligned progress + spend.
- Left column, in order: **Question** (agent attribution eyebrow, 14px body, amber rule — the whole `## Auto Run Result` section) → **Answer** (textarea, hint stating exactly what happens: the blocked story file is archived to `stories/.answers/`, the story is re-planned with the answer as context; a note says to edit `SPEC.md` on the branch instead when the gap is in the spec; actions) → **Or continue in the session** (command block, copy, session lifetime) → **Steps** table (`# · step · type · gate · status · time · harness · cost`), current row promoted to primary text, future rows `QUE`. Gate column prints `liveness / deterministic / human` and, for a checkpointed story, `spec checkpoint` in amber.
- Right column: **Stories** strip (`n/m`, one cell per story: done filled, current amber, future hollow) → **Artifacts** tree at spec-folder scope with changed-since-last-opened chips → **Cost & trace** kv (spent/budget ratio, tokens, wall-clock, your active time, Langfuse trace link, branch link) → **Gate record** (append-only: started, blocked, answered, checkpoint continued, cancelled).
- States: `RUN` — no banner, current step row marked, no Answer section. `CHK` — banner says which checkpoint; the story spec file is shown inline in place of the Question; actions *Continue* / *Cancel run*. `ERR` — banner red; the failing command and its last 40 lines of output in a command block; *Retry step* / *Cancel run*. `DON` — banner replaced by a one-line summary with the PR link.

### 2.3 · Run diagram (`RunDiagram.dc.html`)
- Reached by the `DIAGRAM · DETAIL` toggle in the run's bar (query string `view=diagram`, survives reload). Same header meta line as 2.2; same alert banner rules.
- **Layout:** a left-to-right tree with orthogonal hairline connectors (`{colors.line-strong}`), square nodes on `{colors.surface}`. Column heads `RUN · STEPS · EPICS · STORIES` in `{typography.column-head}`. Root = the run (branch, token, `n/m stories`). Level 1 = the template's steps in order (`checkout`, `baseline`, `stories`, `push`). The `stories` node fans into epic nodes (story-id prefix), each fanning into story nodes.
- **Node:** `{typography.row-title}` name, `{typography.meta}` type or duration, chip + token right-aligned. A story node adds a `{typography.micro}` row of its three sub-steps as words (`build done · verify — · commit —`), never as coloured dots — a second chip on a node would be a traffic light. The current node is promoted to `{colors.text}` and carries the word `now` in `{typography.eyebrow}`; scheduled nodes read `QUE` in tertiary. No node carries more than one signal colour — the token is the signal.
- **Rendering:** the Templates diagram renderer with a run's statuses bound; the two never differ in shape. Read-only; clicking a node switches to DETAIL scrolled to that step's row.
- **Footer readout** under the tree: `step 15 of 22 · story 4-1 build · blocked 2d 04h · 5/8 stories`.
- **States:** `RUN` — the running node green, one only. `BLK`/`CHK` — the stopped node amber; the banner above says why. `DON` — all nodes grey, push node `DON`, PR link in the root. Empty (run queued) — every node `QUE`, root says `waiting: …`.

### 3 · Projects (`Projects.dc.html`)
Two panes: list (name, repositories, runs, one amber/red count if any) and detail: title + meta (litellm key, monthly spend ratio), **Context** (text + hint that it is injected into every prompt), **Repositories** table (`repository · default · quality_gate_command · clone check · status`) with *+ Add repository*, **Credentials** kv (token set/scope, litellm key + budget, env var count), **Runs on this project**. A repository without `quality_gate_command` shows `— none declared` and its status says `verify step will be skipped` — stated here, at configuration time.

### 3.1 · New project (`NewProject.dc.html`)
Form left; **Clone check** readout right, live on save: per repository `ls-remote`, shallow clone (size, seconds), default branch. A failure prints the git output verbatim in an inset block and a one-line fix. One failing repository blocks *Save project*; the form keeps every value.

### 4 · Runs (`Runs.dc.html`)
Bar: project filter + status filter (`ALL · QUE · RUN · BLK · ERR · DON`). **Queue** section: DBOS queue readout (`pos · project · workflow · next step · waiting because · waiting`), with the queue's own parameters in the section head (`concurrency 2 · one active run per repository`). A blocked run appears with `—` position and "waiting for your answer · not queued until then". **History** table: `time · project · workflow · step · type · harness · status · time · cost · trace`, newest first, current rows promoted. Rows link to the run detail scrolled to that step.

### 5 · Templates (`Templates.dc.html`)
Three columns: **versions list** (name, version, pinned-by count, read-only marker), **YAML editor** (line numbers, keys secondary, values primary, step types accent; the selected step highlighted), **Diagram** rendered from the parsed YAML (vertical: node per step with type eyebrow and gate; `for_each` as a dashed group; agent nodes accent-bordered, human gates amber-bordered) + **Inputs bound at start** table. Bar: validation timestamp, *Validate*, *Save as vN+1*. Saving never mutates a pinned version; the list explains this in a hint. Escalation edges are not drawn — they all go to *Needs you*.

## State vocabulary

| Token | Run | Step |
|---|---|---|
| `QUE` | enqueued, or waiting for a repository lock | not yet started |
| `RUN` | a step is executing | executing |
| `BLK` | agent returned `status: blocked`, verify failed twice, budget halt | the step that stopped |
| `CHK` | paused at `spec_checkpoint` (after planning) or `done_checkpoint` (after commit) | the checkpoint row |
| `ERR` | baseline red, infrastructure failure after retries, clone failure | failed |
| `DON` | pushed | done |
| `SKP` | — | skipped (no command declared) — rendered as the word `skipped`, never green |
| `CAN` | cancelled by the operator | — |

## Voice
Unchanged from the 2026-08-25 spine: facts, identifiers, no congratulation. Additions for v1 copy:
- "Blocked story file archived to `stories/.answers/4-1-attempt-1.md` with your answer; story 4-1 re-planned with the answer as context." — say the mechanism, every time.
- "verify step will be **skipped**" at configuration, "skipped — no `quality_gate_command`" at run time.
- "Starts immediately if the repository is free, otherwise queues behind the run holding it."

## Test-ids
The 2026-08-25 grammar `<surface>-<component>[-<instance>][-<field>]` is kept. Surface prefixes for v1: `login`, `nav`, `board`, `newwf`, `wf` (run detail), `projects`, `project-form`, `repo-form`, `runs`, `templates`, `artifacts`. Ids in the mockups are the seed of the contract; the full table is written when the front-end stories are cut.

## Deltas from the 2026-08-25 spine, stated
1. Board columns are status, not pipeline stage (one template, real concurrency).
2. No Notifications surface; "Needs you" column + rail count.
3. No G2/G3 pages; checkpoints live inside the run detail.
4. Answer box is the primary reply path (archive + re-plan with the answer as context — the in-place `## Human Answers` append was rejected at PRD review because build-auto preserves the old intent contract on a draft resume); the resume command is secondary.
5. Signal palette reduced to green / amber / red + greys.
6. New workflow is a page with pre-flight, replacing the G2 plan review.
7. Templates are editable YAML with a rendered diagram (the PRD's "editing is git" is relaxed; versions are immutable once pinned).
8. Board columns are five **equal fluid** columns filling 1440px (not the 08-25 spine's assumed fixed 232px + horizontal scroll); they still never collapse or size to content.
9. Dense tables (steps, runs history, repositories) are a **different component** from the five-column record row: they carry as many columns as the data has, keep the same type roles and hairlines, and the status token stays the only signal-coloured cell in a row.
10. Signal colour allowances beyond chip + token, made explicit: the rail's "n need you" count, a column header, the 2px alert-banner rule, an aged wait, the single warning/failure line in a readout, the login rejection line. Cards carry no coloured border and no coloured words — the token (and an aged age) is the only signal on a card.
