- (event) UX run scoped to M1 surfaces only, per PRD _bmad-output/planning-artifacts/prds/prd-ai-orchestrator-2026-08-24/prd.md (status final). M2 shaping-session UI explicitly out of scope.
- (decision) HARD CONSTRAINT for this run: every interactive element gets a stable data-testid. PRD FR-24a requires acceptance criteria to name test-ids and routes; this UX spec is intended to BE the interface contract that ai-orchestrator's own Playwright suite is generated from. This is not decoration - it is the artifact that unblocks FR-3b (a repo without an e2e_command cannot run the pipeline, so ai-orchestrator cannot be dogfooded until its suite exists).
- (note) This run doubles as verification-queue item #1 from the PRD addendum: write acceptance criteria with test-ids for three real features by hand and confirm it is tolerable in practice. If assigning test-ids at design time is painful here, the oracle strategy needs rethinking before anything is built.
- (decision) Working mode: COACHING PATH, creative tools woven in.
- (decision) Visual base: START FRESH, developer-tool aesthetic. No inherited UI system. Reference space is dense keyboard-friendly developer tooling (Linear, Kestra, Temporal, GitHub), not consumer web. Direction to be elicited and rendered as options, not chosen for the user.
- (decision) Density model: DENSE LIST, SPACIOUS DETAIL. The inbox is compact and scannable for triage; opening an item gives a full-width unhurried view carrying everything needed to decide. Two densities for two distinct jobs.
- (note) Central design question for this run, flagged at open: what exactly appears on an inbox card. PRD FR-34 requires 'enough context to reload cold' - the async model dies if reloading context costs more than the pipeline saved.
- (event) Four design directions rendered to .working/ and opened in browser: instrument-dark (severe monospace readout, one colour chip per row, status as a three-letter token), ledger-light (calm editorial paper, groups the queue by what it ASKS OF YOU, status by small-caps and position not colour), signal-alert (high-contrast on-call console, sorted by SEVERITY not age, type stated four ways, hatched red past 48h), blueprint-slate (schematic slate, every row carries a six-stage pipeline strip with a diamond on the halted stage, status read from POSITION before colour).
- (note) Shared data-testid vocabulary emerged across all four directions (nav-*, inbox-filter-*, inbox-row-{slug}[-type|-project|-repo|-title|-hint|-age], inbox-empty-state, detail-* including detail-question, detail-criterion-ac-N, detail-activity-step-N, detail-resume-command, detail-resume-copy), 92-104 test-ids per file. This vocabulary is a candidate for the FR-24a interface contract regardless of which direction wins.
- (note) Each direction encodes STATUS differently, and that is the real choice: instrument-dark uses a token, ledger-light uses grouping-by-ask, signal-alert uses severity ordering, blueprint-slate uses pipeline POSITION. The pipeline-position idea is the only one that answers 'where did it stop' without reading any text.
- (decision) VISUAL DIRECTION CHOSEN: instrument-dark. Severe all-monospace readout on a fixed column grid, one 7px colour chip per row, status read from a three-letter token in the leftmost column. .working/direction-instrument-dark.html is the reference.
- (decision) ARTIFACT MODEL: one shared artifact/spec folder per working feature/version. BMad agents are instructed to write all generated files into that same spec folder. The spec folder path is recorded PER TASK RUN and PER REPOSITORY, and contents are retrieved from the worktree working folder.
- (decision) ARTIFACT VIEWING IS HIERARCHICAL, matching the item level being reviewed: a STORY item shows the files generated in that story's working folder; an EPIC item shows the epic files plus its related stories; a FEATURE/VERSION shows the complete folder including all epics and stories. Full context for the level under review, nothing more.
- (decision) ABANDONMENT ANSWERED: a blocked story is never abandoned individually. The PM/architect rewrites the spec for the WHOLE EPIC, because a blocking question usually implies impacts beyond one story. That triggers a new adjusted workflow starting fresh on the SAME working branch, with the change recorded as a git commit. Stories that are unchanged are skipped.
- (crack) PRD CHANGE REQUIRED: FR-19a in the finalized PRD says a G3 rejection opens a new SESSION with the rejection reason as context, bounded by the FR-19 per-story rework cap. The user's answer replaces this with an EPIC-LEVEL RE-SPEC: PM/architect rewrites the epic spec, a new adjusted workflow is generated, and it re-runs on the same branch skipping unchanged stories. This is a different and larger mechanism than FR-19a describes, and the per-story cap may no longer be the right bound. Requires a bmad-prd UPDATE pass; do not let it drift as a UX-only decision.
- (note) OPEN MECHANISM: how is 'unchanged story' determined? Recommend the ORCHESTRATOR compute it deterministically - content hash of each story's spec section, compared against the version the previous run executed - rather than asking an agent to judge whether a story changed. Deterministic beats LLM judgment for a skip decision that silently omits work.
- (decision) G2 RESOLVED: a DEDICATED PAGE to review and accept, before workflow creation and setup are triggered. Not an inline panel, not an inbox row expansion.
- (decision) IA REVISED - the home surface is a KANBAN BOARD, not the inbox. Cards are features/versions started, each showing status (blocked, in progress, etc) and current step (epic 1, story 3). Filterable by project or repository.
- (decision) NAVIGATION: kanban card -> FEATURE DETAIL page, with the blocked item highlighted and an alert at the top. Clicking the step or the alert -> TASK DETAIL, which carries the how-to-reply instruction.
- (change) The alert/pending-human-action screen from direction-instrument-dark is DEMOTED from home surface to a NOTIFICATIONS SCREEN. The primary mental model shifts from 'what needs me?' (queue) to 'where is everything?' (board).
- (decision) Artifact view stays the DEFAULT detail view. Diff-since-last-viewed is DEFERRED pending evidence from the first real run, but the last-opened/last-viewed TIMESTAMP is tracked from day one so the feature is buildable later without backfill. Likely shape when built: a tab offering full detailed view vs latest changes only.
- (crack) TENSION with PRD FR-47: M1 serializes execution to ONE ACTIVE RUN AT A TIME (global lock, since a single Postgres backs the E2E database). A kanban board's value is showing many things in flight simultaneously - but under M1 exactly one card can ever be in progress, with everything else queued or done. The board is right for M3 when concurrency exists; for M1 its columns will be nearly empty. Not a blocker, but the design should not imply parallelism the engine cannot deliver.
- (note) M1 SURFACE COUNT GREW from 3 to 6: onboarding, kanban home, feature detail, task detail, G2 review page, notifications. Scope expansion on the UX side relative to the PRD's M1 scoping. User's explicit call, made for human simplicity.
- (decision) KANBAN AXIS: columns are PIPELINE STAGES (Spec -> Plan/G2 -> Build -> Review/G3 -> Merged); the card's status is carried by a small COLOUR CHIP (blocked / running / waiting / failed), consistent with instrument-dark's one-chip-per-row language. Progress is read from position, urgency from colour. Blocked is a state ON the card, not a column, so a blocked card keeps its place in the lifecycle.
- (note) RESOLVES the FR-47 serialization tension: stage columns encode lifecycle POSITION rather than concurrency, so a single in-flight feature still reads correctly under a global lock. Status columns would have looked broken. Building the kanban for M1 is therefore sound.
- (decision) G3 gets ITS OWN PAGE, consistent with G2. Carries the artifact tree, the diff, the E2E result, and the merge decision. Rationale: G3 is the last gate before code reaches main and needs the same protection from triage-speed review as G2; FR-52 watches whether this gate ever rejects.
- (assumption) INFERRED, to confirm at review: notifications are in-app only for M1 (Mattermost is M3 per PRD); onboarding follows FR-1 to FR-5 with the four optional commands validated on save per FR-5; empty and first-run states needed for kanban, notifications, and artifact tree; keyboard affordances kept minimal in M1 beyond copy-resume-command.
- (event) Spines distilled. DESIGN.md 444 lines (18 colors, 15 type roles, 28 spacing tokens, 23 component blocks, all 8 canonical sections, values lifted verbatim from direction-instrument-dark.html). EXPERIENCE.md 515 lines with an invented Test-ID Contract section: 211 test-ids across 9 per-surface tables with routes.
- (decision) TEST-ID GRAMMAR codified: <surface>-<component>[-<instance>][-<field>]. Instance is DOMAIN IDENTITY, never an array index. Ordinals permitted only for the activity timeline and plan steps. States are expressed as ATTRIBUTES, not as separate ids.
- (note) VERIFICATION QUEUE ITEM #1 ANSWERED: assigning test-ids at design time proved tolerable and cheap - but ONLY because the grammar was fixed before the tables were written. The grammar-first ordering is the reusable finding, and it should carry into how BMad agents are instructed to write acceptance criteria under FR-24a.
- (note) Two deliberate renames from the direction file, flagged not silent: inbox-* became notifications-* and detail-* split into feature-* and task-*, forced by the IA revision. The direction file's nav-inbox-empty / nav-inbox-detail variants are a mockup artifact and must not reach the product.
- (note) artifacts-tab-changes is RESERVED but not rendered, so the deferred diff-since-last-viewed view cannot be accidentally designed out.
