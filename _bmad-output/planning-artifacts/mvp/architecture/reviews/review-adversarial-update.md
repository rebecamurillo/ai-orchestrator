# Adversarial review — the UPDATE pass

Method as in `review-adversarial.md`: for each mechanism the 2026-09-02 update introduced (prepare commit, `start_sha` ordering, `frozen_test_files`, `harness` table, `plan_stale`, `continue` on `protected_path`, `terminal_resume`, `budget_raise` re-park, `skip_epic` push rule, two Gateway keys, `MAX_ACTIVE_RUNS`, `bmad_version`, group `skipped`, node `label`) I wrote the two most natural implementations one level down that each satisfy every AD sentence literally, and checked whether they agree on shared data shapes, entity ownership and status-mutation paths. Units are the same epics as the previous review (E1 scaffold · E2 projects/repositories · E3 templates/planner/graph · E4 create_run/walker/queue/engine adapter · E5 `git.*`/`shell`/`checkpoint` · E6 agent step/harness adapters/tracing/budget · E7 signals · E8 board/run detail/diagram · E9 runs/queue · E10 protected paths/trajectories), plus the module named when it matters.

Holes H1–H15 of the previous pass are treated as closed; I did not re-open them. Where a new hole is the *same root cause* surfacing through an update sentence, I say so.

Severity: **critical** = a headline product claim (durability, FR-30, harness enablement) is false when the two units are built as written; **high** = the two units cannot integrate without one being rewritten, or a Run hangs / double-writes at runtime; **medium** = they integrate but the UI, history or trajectory lies, or a sanctioned operator flow false-parks; **low** = operational ambiguity.

## U1 — critical — E4 engine adapter/walker vs E6 `agent` executor: the pre-dispatch attempt writes (`attempt` row, `queued → running`, `start_sha`, `frozen_test_files`, `pgid`, `session_id`) have no owning use case and no durable unit of work

**AD text relied on:** AD-8 "`run`, `step_run`, `attempt`, `gate_record` change only through repository ports, in one unit of work per use case, opened by the engine adapter for the step"; "exactly one use case, `apply_step_result(run_id, seq, StepResult)`, applies every execution transition; … step executors return results and never touch status fields"; AD-9 "… → commit `orchestrator: prepare …` → `attempt.start_sha = HEAD` → dispatch"; AD-14 "`attempt.pgid` is recorded before the process is awaited; a re-attempt first kills the recorded group"; AD-17 "`Git.list_files(frame_first_start_sha, …)`, recorded on the frame's first `attempt`"; Seed `attempt.frozen_test_files (first attempt of a story frame only)`; step machine `queued --> running: attempt starts`; `StepResult = {status, gate, output_ref, park, redispatch}` (no attempt fields).

**Reading A (E4, AD-8-literal):** the adapter opens *one* `SQLAlchemyDatasource` unit of work for the engine step, the walker runs the executor inside it, calls `apply_step_result` at the end, and commits once. `apply_step_result` is the only writer, so it is also the one that inserts the `attempt` row and flips `queued → running → done` — all at step end. Every sentence holds. Consequence: `attempt.pgid`, `start_sha`, `frozen_test_files`, `session_id` written by the executor mid-step are *buffered* in the open transaction; a container kill during the 90-minute harness run loses all of them. On restart the DBOS step re-executes; the walker looks for `previous_attempt.pgid` to kill the orphan — there is no previous attempt row — and dispatches a second harness into the same worktree. FR-12's test ("kill the orchestrator mid-Story, restart — exactly one Harness process exists afterwards") fails, and `.git/index.lock` from the orphan halts the new attempt `blocked` at step-01. The interrupted attempt's `start_sha` is gone too, so the WIP commit made by the recovery attempt swallows the agent's uncommitted `tests/**` edits *before* any check; AD-17's guard is bypassed by every restart — the exact bypass H5 was closed to prevent.

**Reading B (E6, AD-14/AD-17-literal):** the executor inserts the `attempt` row, writes `start_sha` + `frozen_test_files` in one write, writes `pgid` before `await`, each through the `AttemptRepository` port *and commits*, because "recorded before the process is awaited" is meaningless otherwise. Every sentence holds too — until E4's adapter, which owns the transaction, either commits under the executor (E6 needs a `commit()` on a port the domain does not declare) or does not (Reading A's data loss). The two epics cannot be integrated without one rewriting its transaction model.

**Third face — who writes the harness result?** `StepResult` has no `exit_code`, `session_id`, `tokens`, `cost_usd`, `ended_at`; AD-11 says `spend_for_attempt` "writes `attempt.cost_usd`/tokens". So E6 writes attempt fields directly (allowed: not "status fields") and `apply_step_result` writes the status — two writers of one row in one step, and `attempt.status` (`running → done|error`) belongs to neither by name.

**Fourth face — `frozen_test_files` reader.** "The frame's first `attempt`" is the *sync* row's attempt under H11 (every row has attempts), which E5 never populates; E6 reading "first attempt" picks it, finds `null`, freezes nothing. Even reading "first `agent` attempt": under Reading A the interrupted attempt 1 has no `start_sha`, so attempt 2 (whose `start_sha` follows the WIP commit of attempt 1's new tests) becomes the freeze point and those tests are frozen against the very redispatch §I was written to protect — the false park returns one attempt later. On `re_review_done`, a re-planned already-done frame freezes the tests an earlier Run's agent wrote; the review pass that touches one parks. That is by design (FR-31, "Accepting is the only way an agent-made test change ships") but nobody said it, and E8's copy will not either.

**Tightened rule — AD-8, replace "in one unit of work per use case, opened by the engine adapter for the step":**
> Every execution of a row is two use cases in two units of work. `start_attempt(run_id, seq) -> Attempt` (called by the walker at the top of the engine step, committed before the executor runs) inserts the `attempt` row (`n`, `started_at`, `status: running`, `engine_ref`) and writes `step_run.status = running` and `run.status = running` when `queued`. Pre-dispatch fields the `agent` executor produces (`start_sha`, `frozen_test_files`, `pgid`, `session_id`) are written by `start_attempt.record(attempt_id, fields)` in its own committed write, before the process is awaited; `start_sha` and `frozen_test_files` are one write. `apply_step_result(run_id, seq, StepResult)` is the second unit of work; `StepResult` gains `attempt: AttemptOutcome{ended_at, exit_code?, tokens_in?, tokens_out?, cost_usd?, provisional?}` and `apply_step_result` is the only writer of `attempt.status` and `attempt.ended_at`. Executors write nothing else.

**AD-17, replace "recorded on the frame's first `attempt`":**
> `frozen_test_files` is written with `start_sha` on the lowest-`n` attempt of the frame's `agent` row that has a `start_sha` (an attempt killed before that write is not the frame's first). `StepContext` carries `frozen_test_files: list[str] | None` (walker-resolved from that attempt; `None` means "compute at your `start_sha` and record"); the `git.commit` executor reads the same field and never recomputes. A frame planned `skipped · already done` and re-planned under `re_review_done` freezes the tests as they exist at its first attempt, including tests an earlier Run's agent wrote — FR-31 applies unchanged, and the Run detail says so on the frame.

## U2 — medium — E6 pre-WIP protected-path check vs E7 `PUT /runs/{id}/files`: the operator's sanctioned `SPEC.md` edit is a hit "attributed to the previous attempt"

**AD text relied on:** AD-17 "before making those commits the `agent` executor checks `Git.diff_names(previous_attempt.start_sha)` and attributes a hit to the previous attempt"; AD-13 "`PUT /runs/{id}/files` … commits the edit immediately as `spec: operator edit (orchestrator)`"; kinds table `agent`: "protected-path check of the previous attempt → WIP commit → …"; FR-18 assumption "if the gap is in SPEC.md the Operator edits SPEC.md on the branch".

**Reading A (E6, literal):** the check runs before every attempt after the first, diffing `previous_attempt.start_sha..working tree`. Between the previous attempt's `start_sha` and now lie: the agent's commits (already checked at its exit), the `spec: operator edit` commits, and nothing else. So the only possible hits are the operator's own edits. The documented flow — story parks `blocked`, operator edits `SPEC.md` inline, presses Answer — parks the *next* attempt `protected path modified: SPEC.md` "attributed to attempt n−1", which already passed its post-exit check. Every AD sentence holds. Reading B (E6, intent): the check runs only when the previous attempt has no post-exit check on record (timeout, kill, restart) — the one case where the working tree carries unchecked agent work. Reading B is what H5 meant; Reading A is what AD-17 says. Built as A, the trajectory records `SPEC.md` as an *accepted agent change* on `continue`.

**Second face — which attempt records the hit.** The executor is running attempt `n`; `StepResult` has no attempt id, so `apply_step_result` writes `error` on attempt `n`, which has no harness fields, no session, no cost — the Steps table shows a phantom attempt that "modified a protected path" before its own dispatch.

**Tightened rule — AD-17, replace the "before making those commits" clause:**
> The pre-WIP check runs only when `previous_attempt.checked_at` is null (the attempt ended without its post-exit check: timeout, kill, restart) and diffs `previous_attempt.start_sha` against the working tree minus every path named by a `spec_edit` gate record since that `start_sha` (`PUT /files` appends `gate_record{event: spec_edit, path}`). A hit is applied to the *current* attempt with reason `protected path modified by attempt {n−1}: {files}`. `checked_at` is written by `apply_step_result` from `StepResult.attempt`.

## U3 — high — E4 walker vs E7 `continue`: `plan_stale` is a park with no row, no `seq`, no attempt and no `continue` edge

**AD text relied on:** AD-7 "Before the first row the walker re-reads every list file … a difference is applied as park `plan_stale: {file}` (AD-13)"; AD-8 "exactly one use case, `apply_step_result(run_id, seq, StepResult)`, applies every execution transition; the walker calls it inside the engine step that ran the row"; AD-13 `continue` valid when `park_kind ∈ {…, plan_stale}`, effect "the recorded plan proceeds", row transition column lists nothing for it; AD-8 "`signal_run` owns … the re-queue of the target row (`run.park_path`)".

**Reading A (E4):** the stale check is not a row, so the walker calls `apply_step_result(run_id, seq=first, StepResult{status: error, park: Park(plan_stale)})` against the first row (`checkout`, a `git.worktree` that never ran). Compliant. Now E7's `continue`: `park_kind = plan_stale` ✓, then "re-queue of the target row" — `run.park_path` is `checkout`, status `error`; `continue`'s admitted edges are `checkpoint → queued|done` and `error → running` (protected_path only). E7 either 409s a signal the PRD table admits, or invents `error → queued: continue (plan_stale)` — a fourth `continue` meaning nobody else knows. And the run diagram shows a red `checkout` node that never executed.

**Reading B (E4′):** the walker calls a new `park_run(run_id, Park)` that writes `needs_you`, `park_kind = plan_stale`, `park_path = null` — a second execution writer, which AD-8's first sentence forbids, and `park_path = null` breaks H14's contract that every park names a row. **Reading C:** `apply_step_result` with `status: planned` — a park on a row that is still `planned`; `continue` re-queues `planned → queued` (an edge reserved for "predecessor done"), and H11's "every execution creates an attempt" now has an execution with no attempt.

**Tightened rule — AD-7, replace "Before the first row the walker …":**
> `plan_run` emits, as `seq = 0`, one row `path = plan`, kind `plan.check`, gate `deterministic`, with `with_resolved = {files: [{path, sha}]}` for every list file it read. Its executor (`steps/plan_check.py`) re-reads each file at the branch head through `Git.read_file` and returns `done`, or `error` with `park: Park(plan_stale, "plan stale: {file}")`. `continue` on `plan_stale` moves that row `error → done` (added to AD-8's edges and to the `continue` row of AD-13); `cancel` is the only other signal. Add `plan.check` to the shipped kinds table; `repo-init@1` has no list file and its row is `done` at once. A plan is never silently executed against a changed list — now as a row every other rule already covers.

## U4 — high — E6 `agent` executor vs E7 `continue` on `protected_path`: "routing resumes on the same tree, no dispatch" has no `HarnessResult`, creates a phantom attempt, and has no edge on a `git.commit` row

**AD text relied on:** AD-13 `continue` effects "`protected_path`: routing resumes on the same tree, no dispatch", row transition "`error → running → routed status`"; AD-8 "`continue` on a `checkpoint`-kind row moves it to `done`, on an `agent` row to `queued` — the only kind test outside `application/steps/`"; AD-17 "`rules/protected_paths.check` runs in the `agent` executor after the harness exits and before routing … and in the `git.commit` executor"; kinds table `agent`: "… dispatch → protected-path check → FR-16 routing → `Gateway.spend` → budget rule"; H11 "every execution of any row creates one `attempt`".

**Reading A (E7, AD-8-literal):** `continue` on an `agent` row → `queued`; the walker wakes, `start_attempt` creates attempt `n+1`, the executor sees `resume_signal.kind = continue` and skips pre-check, WIP, prepare, dispatch, then "routes" — on what? Routing (FR-16) needs the story file *and* the harness exit code ("exit ≠ 0 with a `done` file → error"); the budget rule needs `HarnessResult.usage` as the provisional fallback; `spend_for_attempt(run_id, attempt_id)` is now called with attempt `n+1`, which made no gateway call → empty → fallback to a `HarnessResult` that does not exist → `0`, provisional. Attempt `n`'s spend — the attempt that actually burned money — is *never read*, because the check was cut off at the protected-path hit. The budget can be exceeded by one full attempt with no halt, and attempt `n+1` sits in history with no harness, no session, `$0`.

**Reading B (E7, AD-13-literal):** `error → running` written by `signal_run`, then "routed status" written by… `apply_step_result`, which needs a `StepResult`, which needs an executor run — Reading A again, or `signal_run` runs `rules/routing` itself in the request path (a `Workspace.read` inside a router-opened unit of work, and the spend read too). Neither AD forbids it; AD-13's title does.

**Second face — `git.commit`-raised `protected_path`.** AD-17 runs the check in `git.commit` too; the park is `protected_path` on a `git.commit` row; PRD §4.6 admits `Continue (accept)`. AD-8's kind test covers `checkpoint` and `agent` only: E7 has no edge for a `git.commit` row and 409s; E5's executor was written to see `resume_signal = continue` and commit without the check. The terminal-session flow (FR-21) is exactly how a human-made test edit reaches `git.commit`.

**Tightened rule — AD-13, replace the `protected_path` cell and add one sentence:**
> `continue` on `protected_path` re-queues the row (`error → queued`, any kind; the kind test of AD-8 becomes "`checkpoint` → `done`, every other kind → `queued`"). The resumed executor reads `resume_signal.kind = continue` and `StepContext.previous_attempt` (the walker passes the row's latest attempt): the `agent` executor performs no dispatch and runs only its tail — routing from the story file and `previous_attempt.exit_code`, `Gateway.spend_for_attempt(run_id, previous_attempt.id)`, budget rule — and `start_attempt` is not called (the one row execution without a new attempt; the outcome is applied to `previous_attempt`); the `git.commit` executor commits without the check. Accepted files are recorded on the gate record and copied to `trajectory` by `record_trajectory`.

## U5 — high — E7 `terminal_resume` / terminal session vs E4 walker vs E6: nothing sets `terminal_session`, `signal_run` writes two rows, `planned → queued` has no owner, and the terminal attempt bypasses spend and routing

**AD text relied on:** AD-13 signal enumeration (`… cancel, terminal_release, terminal_resume`) — no signal *starts* a terminal session; FR-21 "Copying the command marks the Run `terminal session in progress`"; AD-13 `terminal_resume`: "the `agent` row → `done` (actor `terminal`), gate_record | verify runs | `blocked → done`, verify `→ queued`"; AD-8 "`signal_run` owns every operator transition on the Run and the re-queue of the target row (`run.park_path`) … the walker on wake only reads"; step machine `planned --> queued: predecessor done or skipped`; AD-11 "called after every `agent` attempt … before verify".

**Face 1 — who writes `terminal_session = true`.** Reading A (E8): copy is a browser event; `terminal_session` is island state; nothing reaches the server → `terminal_poll` ("over Runs with `terminal_session and status = needs_you`") polls nothing, `terminal_resume` never fires, and the disabled Answer/Continue buttons come back on the next poll refresh. Reading B (E7): a `POST /runs/{id}/terminal` that writes the flag — a Run write outside `signal_run`, the "ad-hoc resume path" AD-13's Prevents names. Both literal.

**Face 2 — who queues `verify`.** `signal_run` re-queues "the target row (`run.park_path`)" — the `agent` row, which `terminal_resume` sets `done`, not `queued`. `verify → queued` is a *second* row, `planned → queued`, an edge the step machine labels "predecessor done" — an execution transition. Reading A (E4): the walker's next row is the first row in `seq` order with status `planned | queued`, so nobody needs to write `queued`; Reading B (E4′): the walker runs only `queued` rows and `apply_step_result` moves the successor `planned → queued` when it writes `done|skipped` — so after `terminal_resume` (which bypasses `apply_step_result`) `verify` stays `planned`, `run.status = running`, and the Run hangs with nothing runnable. AD-8 supports both; the sentence "the walker on wake only reads" was written for the `retry` case and does not say what it reads.

**Face 3 — the terminal attempt.** The operator's `docker compose exec backend-api claude --resume <id>` runs without `env_for(attempt)`: no `x-litellm-session-id`, no `langfuse_session_id`, so its spend lands under no Run (`Gateway.spend_for_attempt` for attempt `n` never sees it) and the budget rule — "called after every agent attempt … before verify" — is skipped entirely because `terminal_resume` goes straight to `verify`. The row is `done` with exit code unknown and the session id of attempt `n`; `record_trajectory` counts it as an agent attempt at attempt-`n` cost.

**Tightened rule — AD-13:**
> Add `terminal_start` to the enumeration (valid when `park_kind ∈ {blocked, checkpoint, verify_failed, misconfigured, timeout, internal}` and `harness.capabilities.resume`; writes `terminal_session = true`, gate_record). `resume_command(cwd, session_id)` prefixes `env ORCH_RUN_ID=… ORCH_ATTEMPT_ID=… ORCH_STORY_ID=… ORCH_HARNESS=… ORCH_PROJECT=… ORCH_TAGS=… ORCH_LANGFUSE_TAGS=…` so terminal calls are attributed to the parked attempt. `terminal_resume` reads `Gateway.spend_for_attempt` for that attempt and applies the budget rule before writing the row `done` (a breach parks `budget` instead). The walker's next row is always the first row in `seq` order whose status is `planned | queued`; `queued` is written only by `start_attempt` (U1) and by `signal_run` on the target row; `planned` rows are runnable when every lower `seq` is `done | skipped`.

## U6 — high — E7 `budget_raise` vs E4 walker vs E6: a `blocked`/`checkpoint` row "re-parks immediately" but nobody may write that park, and the Question was overwritten by the budget park

**AD text relied on:** AD-11 "`spend_usd > budget_usd` parks the Run with `park_kind = budget` while the row keeps its routed status … a `blocked` row re-parks as `blocked` at once, without a dispatch"; AD-13 `budget_raise`: "`signal_run` writes `run.budget_usd`, gate_record | effects none | the walker resumes at the row's routed status (`blocked`/`checkpoint` re-park immediately; `done` continues)"; AD-8 "A `StepResult.park` makes it write `run.status = needs_you`, `run.park_kind`, `run.park_path` and *one* `gate_record` together"; "the walker on wake only reads"; Run machine has `needs_you → running` and no `needs_you → needs_you`.

**Reading A (E4):** `signal_run(budget_raise)` writes `running` and signals; the walker wakes, finds the row `blocked`, and must produce `needs_you / blocked / gate_record{blocked, text = the Story's ## Auto Run Result}`. Only `apply_step_result` may, and it needs a `StepResult` — so the walker synthesises one. The reason text lives in the story file: the walker reads the worktree (a `Workspace` read from `infrastructure/dbos/walker.py`, allowed by AD-2, but "the walker on wake only reads" meant the database) or re-runs the executor, which dispatches — forbidden. Either way the E6 executor's `StepResult{status: blocked, park: Park(budget, …)}` at the original park wrote *one* gate record, `budget`, so the `blocked` Question text exists nowhere in the database; the Run detail after `budget_raise` shows `BLK` with an empty Question.

**Reading B (E7):** `signal_run(budget_raise)` sees the row `blocked`, writes `run.status = needs_you, park_kind = blocked`, appends `gate_record{blocked}`, and does *not* call `engine.signal` — the adapter's `recv` is still pending, which is exactly right. But `needs_you → needs_you` is not a Run transition in AD-8, the gate_record text is again the missing Question, and "the walker resumes at the row's routed status" is now false (the walker never woke). Built together: E7 writes `needs_you`, then signals anyway (the table says nothing about not signalling); the walker wakes into a `needs_you` Run, `apply_step_result` no-ops ("logged no-op when `run.status ≠ running`") and the step returns — the DBOS workflow now proceeds to the *next* row while the Run shows `BLK`. A parked Run whose verify is running.

**Tightened rule — AD-11 + AD-13:**
> A budget park on a row whose routed status is `blocked | checkpoint` appends two gate records in one write: the row's own park (`blocked` with the Question / `checkpoint`) then `budget`. `budget_raise` on such a row writes `run.status = needs_you`, `run.park_kind = row.status`, keeps `park_path`, appends `gate_record{budget_raise}` and does **not** call `engine.signal` (the pending `recv` is the row's own wait); the Run machine gains `needs_you --> needs_you: budget_raise on blocked/checkpoint`. `budget_raise` on a `done` row writes `running` and signals; the walker continues at the next runnable row (U5).

## U8 — high — E4 pre-flight `_bmad/` at `plan_ref` vs E2 `POST /repositories/{id}/init` and `clone_check.bmad_version`: FR-30 cannot start on the repositories it exists for, and the two `_bmad/` opinions disagree with the wrong fix text

**AD text relied on:** AD-16 "Pre-flight requires `_bmad/` at `plan_ref` with `manifest.yaml` version equal to `BMAD_VERSION`"; AD-14 "`repository.clone_check{…, bmad_version}` … reads `_bmad/_config/manifest.yaml` at the default branch (`bmad_version` = its version, `missing`, or `outdated`) … `create_run` returns 409 while it is `failed`"; AD-7 `plan_ref` = `origin/{branch}` when it exists, else `origin/{base}`; FR-8 fix text "run Initialise repository and merge its branch"; AD-10 readiness "an `epic@1` Run on `fixtures/readiness-repo/`".

**Face 2 — default branch vs `plan_ref`.** A working branch cut before `chore/bmad-init` was merged: E2's row says `bmad_version: 6.11.0` (default branch, current), E4's pre-flight says `missing` at `plan_ref` and prints "run Initialise repository and merge its branch" — which the operator already did; the correct fix is "merge `main` into `feat/x`". ## U9 — high — E6 `use_cases/harness_readiness` vs E4 `apply_step_result`: nothing computes the verdict, the `Tracer` port cannot answer it, `version_pin` has no comparer, and `enabled` is read by two units with opposite rules for a Run in flight

**AD text relied on:** AD-10 "table `harness{name, enabled, last_readiness_at, failing_check, version_pin}`, written only by `use_cases/harness_readiness`: a harness is `enabled` only after an `epic@1` Run … reaches `done` **and** the Run trace holds the attempt's spans … **and** `Gateway.spend_for_attempt` returns a non-empty result … `POST /harnesses/{name}/readiness` starts the run"; "A changed `version_pin` disables the harness for new Runs; parked Runs keep it"; AD-11 `Tracer` port: creates the Run trace (no read method); AD-9 "kind-specific branches scattered through the walker" prevented; FR-33 "each check is a line".

The Run finishes hours later inside E4's walker; `apply_step_result` writes `run.status = done` and knows nothing about harnesses (AD-8 lists what it writes). Reading A (E6): `harness_readiness.evaluate(run_id)` exists and waits for someone to call it — a `gate_record` consumer, which the Deferred list says is a later feature. Reading B (E4): the walker, when the Run's project is `readiness`, calls `harness_readiness.evaluate` — a project-specific branch in the walker. Reading C: `POST …/readiness` blocks until the Run ends — "a use case never blocks". Built as A+A: the harness is never enabled and New workflow has no harness to offer; the product cannot start a Run on day 3. Even with a caller, Langfuse ingestion is asynchronous: evaluating at the `done` instant reports `failing_check: trace missing` for a healthy harness, and `Tracer` has no `spans_for_attempt` — E6 either extends the port (fine, but unstated) or imports `langfuse` in a use case (AD-2 violation).

**Face 2 — `version_pin`.** The pin comes from `CLAUDE_CODE_VERSION` etc. in the environment; "a changed `version_pin` disables" needs someone to compare the env pin against the stored pin at startup and write `enabled = false`. **Tightened rule — AD-10:**
> The verdict is computed by the scheduled job `readiness_check` (every 60 s, `engine.schedule`) over Runs of project `readiness` that are terminal and whose `harness.readiness_run_id` matches and has no verdict; it retries the trace and spend lines for up to 10 minutes after `done` before recording `failing_check`, and writes `enabled`, `last_readiness_at`, `failing_check`. `Tracer` gains `attempt_observed(run_id, attempt_id) -> bool` (spans under the trace for `claude`/`codex`; generations under `session = run_id` for `local`). `harness_readiness.sync_pins()` runs from `main.py` before `DBOS.launch()` and disables any harness whose env pin differs from `version_pin`. `harness.enabled` is read only by `create_run`, pre-flight and `GET /harnesses`; a Run carries `run.harness` and every executor dispatches on it regardless of `enabled` — queued and parked Runs alike keep their harness.

## U13 — low — E4 engine adapter vs E9 queue read model vs deploy: `MAX_ACTIVE_RUNS` is "an instance setting" with no stated read time, restart or version rule

**AD text relied on:** AD-12 "global concurrency `MAX_ACTIVE_RUNS` (instance setting, default 2)"; AD-6 "`application_version` … bumped deliberately when the walker's step sequence changes, after draining active Runs"; research/dbos.md "`DBOS.register_queue(name, global_concurrency=…)` before launch"; AD-12 reason `global concurrency, held by {runs}`.

**Reading A (E4):** `register_queue` reads the setting once at `main.py` before `DBOS.launch()`; a change is a container restart; no drain, no `DBOS_APPLICATION_VERSION` bump (queue parameters are not workflow source; PENDING Runs recover unchanged). **Tightened rule — AD-12, add:**
> `MAX_ACTIVE_RUNS` is read once by the engine adapter's queue registration at startup; changing it is a container restart, never a drain and never a `DBOS_APPLICATION_VERSION` bump; PENDING Runs continue under the new limit. `list_queue()` derives the reason: `repository lock held by {run}` when a non-terminal Run targets the same repository, else `global concurrency, held by {runs}` (the non-terminal Runs holding slots); it never reads the limit.
