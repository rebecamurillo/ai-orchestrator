AI Orchestrator Solution Design

How the MVP is put together, why each seam sits where it does, and what an epic built against it may and may not decide. The terse contract is ARCHITECTURE-SPINE.md; this page is the walkthrough.

spine _bmad-output/planning-artifacts/mvp/architecture/ARCHITECTURE-SPINE.md decisions AD-1 … AD-20 written 2026-09-02 · updated the same day after the PRD's reviewer gate binds FR-1 … FR-33, NFR-1 … NFR-9

What it is

A dispatcher and a readout. A senior engineer writes a spec folder on a branch, points the orchestrator at it, and walks away. The orchestrator checks the branch out, confirms the repository is green, and sends each story to a coding-agent harness in unattended mode. The agent plans, implements, reviews and commits; the orchestrator verifies with the repository's own quality command and moves on. It stops only where the spec author declared a checkpoint or where an agent could not proceed without a human, and when it stops, one screen shows what it needs.

Three harnesses run from day one, Claude Code, Codex CLI and OpenCode over local models, all through one LiteLLM gateway, all visible in Langfuse under one session per run, with one cost.

Shape and layers

Two deployables in one compose file. web-client is an Astro multi-page app on Node with React islands for the interactive parts. It is the browser's only origin: it checks the session cookie, renders pages, and proxies /api/* to the backend with the bearer token. backend-api is a Python service in one container with the harness CLIs pre-installed: FastAPI routes per feature, the durable walker, git and process control.

Inside backend-api the paradigm is clean architecture. The domain holds entities, status machines and the port protocols. The application holds use cases, the step kinds and the template validator and planner. The API and the infrastructure both depend inward; nothing in domain or application imports FastAPI, SQLAlchemy, DBOS, subprocess or the filesystem. A linter enforces the direction in CI.

The API contract is owned by the backend. Pydantic schemas produce openapi.json; the web client generates its TypeScript types from it and CI fails on drift. Nobody writes an API type by hand in TypeScript.

Life of a Run

Planned completely before anything executes

Starting a run does not start a workflow that discovers its steps as it goes. A pure function reads the pinned template version, its callee templates and the list files (epics.yaml, stories.yaml) straight from the remote branch, and expands the whole tree into rows: one per step, with a dense sequence number, a path such as epics[0].stories[3].build, a human label (epic 1 · story 4-1 · build), its resolved parameters, and status planned. The first row of every plan is plan.check: when the run finally starts it re-reads the list files at the branch head and parks the run as plan stale if they changed, so a plan is never silently executed against a branch that moved. Pre-flight's "What will run" is that same function without persistence. Only after the rows are stored is the run enqueued.

Three shipped templates compose by call: initiative loops over epics and calls epic, which loops over stories and calls story. A fourth, repo-init, prepares a repository for the method. The PRD's dev-loop is exactly initiative → epic → story; story is a callee only, since it has no checkout of its own, so New workflow offers initiative, epic and repo-init. Each epic names its branch in epics.yaml; consecutive epics on one branch stack, different branches get their own worktree and compare link.

Walked by a durable engine that only reads the plan

DBOS provides durability, but it sits behind an application port. The walker executes rows in sequence order, each inside an engine step; a restart resumes at the last completed row, and a completed row is never re-run. Executors are pure over the ports and return a result; two use cases own execution writes: start_attempt opens the attempt in its own transaction before the executor runs, and apply_step_result applies the completion, writes the gate record and queues the next row. The agent executor records the start commit, the frozen test set and the process group before it waits on the harness, so a restart finds them. If the run needs a human, the result says so, and the engine adapter parks the workflow with a single durable receive, holding the repository lock and its concurrency slot for as long as it waits; after 30 days without a signal the run fails as parked 30 days.

Resumed by signals that write the database, not the worktree

Every operator action is one signal, POST /runs/{id}/signals, validated against the run's current status. The signal handler records the gate entry, applies the transition, re-queues the target row and wakes the engine. The worktree side effects of a signal, archiving the blocked story file with the answer, de-duplicating ambiguous files on retry, committing a skipped story, happen inside the resumed engine step, so they are durable and never done twice. Cancel is the one exception: it kills the harness process group, removes every worktree the run created, and deletes only branches the run created and never pushed.

Guarded by anchors an agent cannot move

Before every dispatch the orchestrator commits what it wrote (project-context.md, an archived answer, a verify-failure note) as a prepare commit, because the build skill refuses a dirty tree; the attempt's start commit is taken after it. After the harness exits, the orchestrator diffs only the agent's own range, start commit to end commit plus anything uncommitted, so an operator edit made while the run was parked can never be blamed on the agent. A modified SPEC.md, stories.yaml, epics.yaml, any AGENTS.md, or any test file that existed when the story's first attempt began parks the run; tests the agent added during the story stay editable on its later attempts. The operator can accept such a change once, and the accepted files are recorded and excluded from the story's later checks. Automatic retries exist only where the pinned template declares them and are always bounded and recorded.

Ports and signals

Seven ports separate the use cases from the world. Each has exactly one production adapter and one in-memory fake shared by every unit test.

PortOperationsAdapter
WorkflowEngineenqueue with a partition key, signal, cancel, list the queue, read an attempt's durable record, schedule a jobDBOS: one queue, partition = repository, concurrency 2; identifiers stored as opaque JSON
Harnessrun, resume, resume command; capabilitiesone adapter per CLI; returns session id, exit code, usage, log path; never interprets output

Workspaceread, write, glob, exists, move, tree, rooted at the run's worktreefilesystem under /work
ProcessRunnerstart in its own process group with a timeout, wait, kill groupsubprocess; owns every timeout
Gatewayspend for an attemptLiteLLM /spend/logs/v2 by end-user id and session id, read with the admin-side spend key
Tracercreate run trace, open attempt span, export traceparent, tell whether an attempt was observedLangfuse SDK

Because DBOS is reached only through the engine port and its identifiers are opaque, replacing it is one adapter and no use case. The same holds for every other port.

Tracing and cost

Creating a run creates its Langfuse trace with a seeded id and the run id as session. Each attempt opens a child span and exports a W3C TRACEPARENT into the harness environment. What each harness can do with it differs, and the spine binds the achievable floor rather than a wish.

HarnessTrace relationMechanism
claude parentedsame trace, child spansnative OTLP export; print mode reads inbound TRACEPARENT; CLAUDE_CODE_PROPAGATE_TRACEPARENT=1 forwards it to the gateway
codex parentedsame trace, child spansnative [otel] export; inbound TRACEPARENT verified in source only, a day-one check
local (opencode) sessionseparate traces, same user idLangfuse plugin; no inbound parent exists

Cost is not read from the harnesses. Every gateway request carries the run id as LiteLLM end-user, the attempt id as LiteLLM session, and a tag set; the open-source proxy records all three, and one query per attempt returns its spend and tokens. Budget is checked after every agent attempt, retries included, before verify, and a halt keeps the row's own status while the run parks for a raise; while the gateway figure is not yet in, the harness's own usage stands in and is marked provisional.

Two gateway keys. The key a harness receives is a LiteLLM virtual key restricted to model routes (key_type: llm_api); it cannot read spend or manage keys. The key that reads /spend/logs/v2 is a master or proxy-admin key held by the backend only, because spend logs are scoped to the calling user otherwise. Issuing both on the host is a day-one check.

Harnesses and BMAD

BMAD cannot be installed globally. Every skill runs _bmad/scripts/render_skill.py from the repository it works on. The image can hold the CLIs, the method package and the skill stubs; the target repository still needs its own _bmad/ folder.

In the image, once

  • Claude Code, Codex CLI, OpenCode at pinned versions
  • bmad-method at the pinned version
  • skill stubs in ~/.claude/skills and ~/.agents/skills
  • one script per harness: install, configure, doctor

In each target repository

  • _bmad/ with config, scripts and custom/ overrides
  • the spec folders
  • .claude/skills/bmad-* and .agents/skills/bmad-* git-ignored
  • version must equal the image's, checked at pre-flight

The shipped repo-init template does the initialisation through the same engine: worktree on chore/bmad-init, install, ignore the skill folders, commit, push, compare link. Upgrading BMAD is an image rebuild plus one repo-init run per repository.

Harness config files under the agent home reference environment variable names only. Per-attempt values, run id, attempt id, story id, tags, trace parent, gateway key, arrive through a fixed environment contract declared once in _common.sh and populated by the adapter, with each harness script naming the native aliases it derives (Claude's auth token and custom headers, OpenCode's Langfuse variables), so two concurrent runs never race on a shared config file and a unit test can assert the key set. Readiness is state: a harness is offered in New workflow only after an epic run on a one-story fixture repository, built at container start under a built-in readiness project, reached done, its spans were seen in Langfuse, and its spend showed up in the gateway; each check is a line the operator can read, a changed version pin disables the harness until it passes again, and runs already parked on it keep it.

The 20 decisions

Each decision in the spine names what it binds, the divergence it prevents, and an enforceable rule. The one-line versions:

AD-1
Two deployables, one browser-facing origin
The browser talks only to web-client; only its server side calls backend-api, with the bearer. No cookies or CORS on the API.
AD-2
Dependency direction inside backend-api
domain ← application ← api, infrastructure. No framework, engine, filesystem or subprocess imports above infrastructure. Linted.
AD-3
Contract owned by the backend, generated into the client
Pydantic → openapi.json → TypeScript types; CI fails on drift.
AD-4
One secret token, two carriers
Bearer on the API, signed cookie on the web; the same value.
AD-5
Credentials stop at the process that needs them
Git alone sees the GitHub token; harnesses see a model-only gateway key, tracing keys and project env; the spend key stays in the backend.
AD-6
The engine is a port; identifiers are opaque
Six operations; DBOS ids stored as JSON only the adapter reads; application version pinned.
AD-7
Planned completely, purely, from the remote branch
Every row exists with a sequence number before enqueue; nothing executes that is not in the plan.
AD-8
One writer per transition
start_attempt and apply_step_result for execution, signal_run for the operator; executors and routers never touch status.
AD-9
One module per step kind; bounded re-execution
A registry is the only enumeration; retries exist only where the pinned template declares them.
AD-10
Harness adapters behind one port, enabled after a readiness run
Config references env names only; adapters never interpret model output; resume only within a row; readiness is a persisted table fed by an epic run on the fixture.
AD-11
One run, one session; parented where possible; every call attributable
Run id as session, attempt id on every gateway request; spend read per attempt from the open-source proxy.
AD-12
Repository lock is the queue partition
Held for the run's whole life, including while it waits for you.
AD-13
Signals write the database; effects happen in the resumed step
A per-signal table fixes validity, writes and row transition; cancel is the one request-path exception.
AD-14
Filesystem, git and processes go through three ports
One worktree per run and branch, tracked on the run; the process runner owns timeouts.
AD-15
Immutable versions, one validator, one graph builder
Callees pinned transitively; variables do not inherit; the browser only lays out and renders.
AD-16
BMAD in the image and in _bmad/; skill folders never committed
Version equality checked at pre-flight; repo-init prepares a repository.
AD-17
Frozen anchors checked after every agent attempt
Spec, stories, epics, AGENTS.md and the tests that existed at the story's first attempt, checked over the agent's own commit range; a hit parks the run, is never auto-retried, and can be accepted once.
AD-18
Layered tests, shared fakes, checkable gates
Unit on fakes; API E2E with httpx and Schemathesis; UI E2E with Playwright; coverage thresholds in CI.
AD-19
Trajectory capture is a table
One append-only row per done story; exported as JSONL.
AD-20
Configuration is the environment
.env.example is the contract; harness config generated from it at start.

Deferred and open

Deferred, with a home ready

  • Per-repository GitHub tokens: the encrypted column exists
  • Per-project budgets and virtual keys: tags already attribute spend
  • Parallel epics: rejected by the validator until a per-branch lock exists
  • Second backend container: the engine adapter and volumes allow it
  • Live updates over SSE: same endpoints, one store to change
  • Notifications, trajectory outcomes, lockout, secret rotation

Open at handoff, day-one checks

  1. Codex honours inbound TRACEPARENT (source-verified only)
  2. DBOS step id equals the operation output's function id
  3. The Claude tool allowlist that lets bmad-build-auto finish under dontAsk
  4. Global skill stubs resolve the worktree as project root; Codex and OpenCode subagents satisfy the skill
  5. Spend headers coexist with Langfuse session headers
  6. Two gateway keys on the host LiteLLM: a model-only key (key_type: llm_api) for harnesses, an admin key for spend

None of the six blocks the architecture; each is confined to one adapter or the host configuration and has a written fallback in the spine.
