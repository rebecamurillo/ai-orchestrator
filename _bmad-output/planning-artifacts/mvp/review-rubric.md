# PRD Quality Review — AI Orchestrator MVP — dev loop

**2026-09-02 pass.** Reviewed `prd.md` (updated 2026-09-02) and `addendum.md` against the PRD quality rubric; `architecture/ARCHITECTURE-SPINE.md` consulted only where a finding depends on it. Calibration: internal tool, single operator who is also the builder, one-week build, chain-top for `bmad-create-epics-and-stories`. This pass replaces the 2026-08-26 review; it concentrates on internal consistency after the spine update, the AD citations, and the testability of the new FR-30..FR-33.

## Overall verdict

The PRD holds up as a capability spec: the thesis (a dispatcher and a readout, not an autonomous engineer) is specific, every FR carries testable consequences, non-goals and tiers are explicit, and the assumptions index round-trips cleanly. The 2026-09-02 update landed without breaking the FR set — all of FR-1..FR-33 are present exactly once and every one is tiered. What is at risk is downstream precision on three seams: the machine-stop taxonomy is defined in four places and none covers every stop the FRs produce; the composition of the shipped `story` Template is left implicit, so a standalone `story` Run — which FR-8 offers and FR-33 depends on — has no stated checkout; and the concurrency rule hides a trade-off (a parked Run occupies a global slot for up to 30 days) that the Operator will hit. None of these is hard to fix; all three would otherwise be resolved by story creation guessing.

## Decision-readiness — strong

Decisions read as decisions: `codex` is MUST "because SM-3 exists to compare Harnesses" (§6.1); `local` ships only if §8 items 6–7 resolve, with a named fallback (addendum §C); "Slips first, in order" (§6.1) is an ordered de-scope list rather than a hope. Trade-offs name what was given up — addendum §C's rejected alternatives each carry a reason, and the 2026-09-02 changes (`Gateway virtual key per Project` dropped, `Steps created as the Run progresses` replaced) say why. The open questions in §8 are genuinely open: items 1–4 each have a day, a test (the FR-33 readiness run), and a fallback; none is answered in its own next sentence. The `--bare` resolution is recorded as resolved with evidence rather than deleted.

One trade-off is not surfaced. FR-13 says a `needs-you` Run "**holds** its lock" and explains why; it does not say whether a parked Run also counts against "at most two active Runs overall". The spine (AD-12: "The lock is held for the Run's whole life, including `needs_you`", on a queue with global concurrency 2) makes it count. So two parked Runs — the exact situation UJ-3 describes, over "two days" — stop every other Repository from running for up to 30 days (FR-12). The PRD should either state that consequence or decide differently.

### Findings
- **high** A parked Run silently consumes a global concurrency slot (§4.4 FR-13; §4.6) — "at most two active Runs overall" does not say whether `needs-you` is active; the spine's mechanism makes it so, meaning two `needs-you` Runs block all Runs on every other Repository until answered. This is a real operational trade-off of AD-12 that the PRD's own UJ-3 ("Two days later, one card is amber") walks into. *Fix:* add a consequence to FR-13: "A `needs-you` Run holds its Repository lock **and** one of the two global slots; the queue row reads `global concurrency` and names the parked Runs." Then add a `[NOTE FOR PM]` naming the alternative (global concurrency counts only `running`) and why it was rejected, or adopt it.
- **low** `[NOTE FOR PM]` callouts sit only in §6.2 (multi-repository, `unit_test_command`) — both real tensions, but the PRD has others with no callout: the FR-13 slot question above, and the FR-32 tiering question under Strategic coherence. *Fix:* add callouts at those two.

## Substance over theater — strong

Nothing here is furniture. The Vision (§1) could not swap into another orchestrator PRD: it names the files (`SPEC.md`, `stories.yaml`, `epics.yaml`), the skill (`bmad-build-auto`), the three harnesses, and the one thing the MVP is not. The three UJs each drive decisions traceable to FRs (UJ-1 → FR-4 verbatim git output and value retention, FR-30; UJ-2 → FR-8 *What will run*, FR-13 lock message; UJ-3 → FR-18 archive mechanism, FR-19, FR-20 skip). NFRs carry product-specific bounds — NFR-2 names its test ("a Template with a Step lacking `gate`"), NFR-6 gives the exact colour rule, NFR-7 gives "under 30 minutes on the Mac mini". Counter-metrics (SM-C1..C3) are argued, not listed.

The one section that is architecture wearing an NFR label is NFR-9 *Buildability*: "strict layering enforced by a linter, a formatter and linter per stack, unit tests on shared fakes … a step kind, a Harness, or the workflow engine can be replaced by adding one adapter without touching use cases (AD-6, AD-9, AD-10)". These are the spine's AD-2/AD-18 restated. They are true constraints on the build week, but they are not observable properties of the product; see the leakage finding under Downstream usability.

### Findings
- **low** NFR-9 restates spine invariants as a product NFR (§10 NFR-9) — the content belongs to the spine, which the PRD already names as binding. *Fix:* reduce NFR-9 to one line: "Buildability constraints are the spine's AD-2, AD-6, AD-9, AD-10, AD-18; the PRD adds none." Keep the FR-level observables (e.g. FR-14 "Harness static configuration … references variable names only") where they are.

## Strategic coherence — strong

There is a thesis and the features serve it: "a story-sized unit of work runs to a verified commit without anyone watching" (§1), and the three-harness design exists for SM-3. Prioritisation follows the thesis — MUST is the loop plus the honesty of the readout; the diagram, inline edit, and history are SHOULD; lockout and LIST view are COULD. Success metrics validate the thesis rather than measure activity: SM-1 (unattended completion, per Harness, with a target only for `claude`), SM-2 (cold reload, measured by the FR-23 active-time mechanism the PRD actually specifies), SM-3 (cost and time per done Story per Harness). Counter-metrics are present and reasoned.

One tension between §6.1 and §7. FR-32 says "The record carries what SM-1 and SM-3 need per Story; no separate metric table exists" — yet FR-32 is SHOULD. If it slips, the two primary metrics have no stated data source. SM-3 could be reconstructed from FR-28 Attempt records and SM-1 from the gate record, but the PRD says the opposite ("no separate metric table"), so story creation would not build that path.

### Findings
- **medium** Primary metrics depend on a SHOULD-tier FR with no fallback (§4.9 FR-32; §6.1 Tiers; §7 SM-1, SM-3) — "no separate metric table exists" plus FR-32 in SHOULD means a slip removes the measurement of the two metrics the MVP exists to produce. *Fix:* either promote FR-32's record-writing bullet to MUST (export stays SHOULD), or state in §7 that SM-1 is computed from the gate record (Runs `done` with no Signal other than `continue`) and SM-3 from Attempt rows summed per Story Path, with FR-32 as the convenience export.

## Done-ness clarity — adequate

Most FRs are unusually testable for a PRD: exact messages (`token rejected — n attempts left`, `waiting: repository lock held by {run}`, `verify failed 2/2`), exact paths (`/work/{project}/{repo}/wt/{branch}`, `stories/.answers/{id}-attempt-{n}.md`), exact commit messages, timeouts with defaults, a kill-and-restart test in FR-12. The new FR-31 is fully testable (the set of Protected paths, the comparison baseline "after the interrupted-work commit of FR-12", the outcome, the non-retry). FR-30 and FR-33 are testable at the outcome level but leave the entities they touch unstated; FR-32 is testable but two of its fields are unnamed.

The largest gap is not an FR but the composition §4.4 asserts: "`initiative` → for each epic {`epic` → checkout → baseline → for each Story {`story` → sync → build → verify → commit-guard [→ done checkpoint]} → push → compare link}". Read literally, checkout and baseline belong to `epic`, and `story` is sync → build → verify → commit-guard. But FR-8 offers `story` as a Run ("for `epic` or `story`: the Spec folder"), §6.1 makes the `story` Template MUST, and FR-33 runs "the shipped `story` Template on a fixture Repository". A `story` Run with no checkout has no Worktree to sync into. The PRD never says what `story@1` contains; the spine does not either. Story creation will have to invent it.

FR-17's budget check reads "the Attempt's spend is read from Gateway spend logs … when the Harness process exits, before the verify Step", but FR-28 concedes the Gateway figure may not yet be available ("harness-reported usage is shown as provisional until the Gateway figure for the Attempt is available"). What the budget rule does when the figure is empty or partial at check time is not stated — treat as $0 and continue, wait, or halt?

### Findings
- **high** The shipped `story` Template's steps are never stated, and the loop in §4.4 implies it has no checkout (§4.4 description; FR-8; FR-33; §6.1) — a standalone `story` Run and the FR-33 readiness run both need a Worktree; §4.4 places checkout and baseline under `epic`. *Fix:* add one line to §4.3 or §4.4 listing each shipped Template's steps: e.g. "`story`: worktree (idempotent, FR-12) → sync → build → verify → commit-guard; `epic`: worktree → install → baseline → for each Story → `story` → push → compare link; `initiative`: for each epic → `epic`." If `story` reuses the caller's Worktree when called, say that the `git.worktree` Step is a no-op on an existing Worktree.
- **medium** Budget halt behaviour when Gateway spend is not yet available is unstated (§4.5 FR-17; §4.9 FR-28) — the check runs at process exit, but spend logs may lag; the rule "if spend > budget" is undefined on a missing figure. *Fix:* add a consequence: "If no Gateway row exists for the Attempt at check time, the check retries for up to N s, then uses the harness-reported figure and records the Attempt cost as provisional; a provisional figure never halts the Run on its own" (or whichever rule the Operator wants).
- **medium** FR-33's pass criteria are named but not defined per Harness, and the readiness Run's place among entities is unstated (§4.5 FR-33) — "trace continuity" has different pass conditions for `claude`/`codex` (parented spans) and `local` (session only, per §9 and FR-27); the run happens on a "fixture Repository" that is not a registered Repository under any Project, yet it is a Run (Board column? Project tag `project:`? Repository lock?). *Fix:* add two consequences: the per-Harness trace-continuity pass condition (reuse FR-27's two cases), and "The readiness Run belongs to a system Project `_readiness` and its fixture Repository; it appears on the Board like any Run and is subject to FR-13."
- **medium** FR-30's Repository-row state depends on the Clone check reading the method version, which FR-4 and the Glossary do not include (§4.2 FR-30, FR-4; §3 *Clone check*) — "from the last Clone check" but the Clone check is defined as `git ls-remote`, shallow clone, default branch exists. Also, pre-flight's stated fix for a missing `_bmad/` on the **Working** branch is "`run Initialise repository`" (FR-8), but FR-30 pushes `chore/bmad-init` from the default branch; the Operator must also merge it into the default branch and then into the Working branch before pre-flight passes. *Fix:* add a fourth check to FR-4 and the Glossary ("`_bmad/_config/manifest.yaml` version on the default branch, or `missing`"); change FR-8's fix text to "`run Initialise repository`, merge `chore/bmad-init`, then update the Working branch".
- **low** FR-31 does not say whether the comparison includes the agent's commits (§4.5 FR-31) — "compares the tree against the commit recorded when the Attempt started"; since the agent commits its own work (§4.4), the check must diff HEAD plus the working tree against `start_sha`, not the working tree alone. *Fix:* "compares HEAD and the working tree against the recorded commit".
- **low** FR-32's record fields "Attempts" and "gate results" are unshaped (§4.9 FR-32) — a count or a list; which gates. *Fix:* "Attempts (count, and per Attempt: harness, model, exit code, cost), gate results (verify exit code, protected-path outcome, checkpoint decisions)".
- **low** Plan source when the Working branch does not exist is unstated (§4.4 FR-8) — "Every planned row is read from the remote branch at one commit" but FR-9 allows a Working branch that does not exist yet. *Fix:* "read from the Working branch when it exists, else from the base branch" (this is what the spine's AD-7 does).
- **low** Inline edits to `stories.yaml` mid-Run have no effect on the plan and the PRD does not say the UI states this (§4.6 FR-19; FR-10 "never re-read during the Run"). *Fix:* one sentence in FR-19: "Edits to `stories.yaml` or `epics.yaml` do not change the planned rows; the editor says so."

## Scope honesty — strong

§5 Non-goals does real work (never merges, never force-pushes, not a visual editor, does not commit skill folders). §6.2 names each deferral with its landing place. `[NON-GOAL for MVP: creating the pull request]` sits exactly where a reader would assume otherwise (FR-11). Ten `[ASSUMPTION]` tags, all indexed in §9; two `[NOTE FOR PM]`; seven open questions of which four block and three are deferred with a reason. For internal stakes on a build-and-dogfood-in-a-week tool, that density is right.

One assumption is a bet on skill behaviour rather than a product choice and is not on the day-1 verification queue: FR-10's `[ASSUMPTION: the implementation step reads the appended Verify Failure section as part of the spec]`. Addendum §G records the re-dispatch design (set `status: in-progress`, route to step-03) but the FR-33 readiness run uses a trivial Story that never fails verify, so nothing in the plan exercises this path before day 5. If the assumption is wrong, verify redispatch — a MUST — degrades to "re-run and hope".

### Findings
- **medium** The verify-redispatch assumption is unverified by any planned check (§4.4 FR-10 assumption; §8; addendum §H) — the readiness run cannot exercise it and §8 does not list it. *Fix:* add it as §8 item 5 ("Does `bmad-build-auto` step-03 read `## Verify Failure` when re-entered at `in-progress`? Day-1 check on the fixture Repository with a deliberately failing quality command; fallback: prepend the failure tail to the re-dispatch prompt").
- **low** `pause_before_item_when` is accepted by the validator with no PRD consumer (§4.3 FR-5) — the spec checkpoint is a status of the Story step, the done checkpoint is `pause_after_item_when`; nothing uses a before-row. *Fix:* either state its purpose or mark it "accepted, unused by shipped Templates" alongside `unit_test_command` in §6.2.

## Downstream usability — adequate

This PRD is chain-top for story creation and mostly extracts cleanly: the Glossary is long and used consistently (Run, Step, Attempt, Path, Gate strength, Signal, Question, Answer), every FR has a section, and the addendum keeps mechanism out of the FRs where it can. Three things will cost the story writer time.

**Stop taxonomy.** The set of machine stops is stated in four places: the Glossary *Gate record* events (`blocked | checkpoint | verify_failed | budget | timeout | push_rejected | protected_path | misconfigured | internal`), the Glossary *Status* `BLK` list, the §4.6 description ("agent `blocked`, Checkpoint, verify failed twice, budget halt, Step timeout, push rejected, Protected path modified, internal error, and the configuration failures listed in FR-16"), and FR-20's Retry list ("timeout, harness exit, push rejected, misconfigured, internal, verify failed"). None of them covers all the stops the FRs create: `sync: branch diverged` (FR-10), `no story file` / `ambiguous story file` (FR-16), `unexpected status: {status}` / `harness exit {code}` (FR-16), `re-baseline failed after skip` (FR-20). Which gate-record event each writes, which `BLK` reason the card shows, and whether Retry is offered (FR-10 says yes for sync, FR-16 yes for story-file errors, FR-31 yes for protected path — but FR-20's list omits all three) is left to inference. The gate record, the banner, the Retry button, and the queue reason are each a story; they will diverge.

**AD citations.** Citing spine `AD` ids is acceptable here and is a net help — for a single-operator PRD whose builder is the reader, "bound by AD-13" tells story creation where the invariant lives without restating it. The leakage is not the citations; it is a handful of bullets that state an implementation mechanism *as a testable consequence*: FR-13 "there is no separate lock table"; FR-10 "The timer belongs to the process runner, never to the workflow engine"; FR-25 "read from the workflow engine's queued workflows through its port, not from a separate table"; FR-7 "the browser never parses YAML"; FR-23 "the browser aggregates nothing across requests". None is observable from the product; each will become an acceptance criterion that tests code structure. The fix is labelling, not deletion.

**DSL source of truth.** FR-5 accepts "the DSL v1" and then says "The full key table is the spine's 'Template DSL v1 keys'", while the frontmatter also lists `template-dsl-draft.md` as an input. The spine's table includes keys the PRD never mentions (`escalate_when`, `pause_when`, `resume_session`, `id`, `description`, `required/default/values`), and addendum §G withdraws `pause_when` ("cannot hang off the `agent` Step alone") while the spine still lists it. FR-5's "rejects anything else" is therefore not checkable from the PRD, and the two lists disagree.

### Findings
- **high** Machine stops are enumerated in four places and none is complete (§3 *Gate record*, *Status*; §4.6 description; FR-20 Retry; vs FR-10 sync, FR-16 story-file and status errors, FR-20 re-baseline) — six stop reasons named by FRs have no gate-record event, no `BLK` reason, and an inconsistent Retry answer. *Fix:* make the Glossary *Gate record* the single enum, extend it (`sync_diverged`, `story_file` for no/ambiguous, `unexpected_status`, `harness_exit`, `rebaseline_failed`), and have §4.6, the `BLK` list, and FR-20 say "every event of the gate record enum except `checkpoint` and `budget`" (Retry) rather than re-listing. Keep it aligned with the spine's `Park.kind` (AD-8, AD-13), which today matches the PRD's shorter list.
- **medium** Mechanism stated as testable consequence (FR-7 "browser never parses YAML"; FR-10 "timer belongs to the process runner"; FR-13 "no separate lock table"; FR-23 "browser aggregates nothing"; FR-25 "not from a separate table") — not observable from outside; will surface as structural acceptance criteria in stories. *Fix:* move each to a trailing line `*Bound by:* AD-n` under the FR, leaving the observable half (e.g. FR-25 "the queue and the engine's view never disagree"; FR-7 "the diagram equals the validator's graph for the same YAML") as the consequence. Keep every other AD citation as is.
- **medium** FR-5's key set is delegated to the spine and the two disagree (§4.3 FR-5; frontmatter inputs; spine "Template DSL v1 keys"; addendum §G on `pause_when`) — story creation cannot write the validator's acceptance list from the PRD; `escalate_when` and `pause_when` are accepted by the spine and unmentioned or withdrawn by the PRD. *Fix:* either inline the key table in FR-5 (it is one short table) or name the spine table as the sole source and drop `template-dsl-draft.md` from the inputs; in both cases reconcile `pause_when` / `escalate_when` (accept and describe, or reject).
- **low** Two names for the Story step (§3 *Step* "Story step"; UJ-2 and FR-29 "build"; FR-32 "build Step") and an undefined screen name ("New workflow" in UJ-2, FR-14, FR-33 for the screen that creates a Run). *Fix:* Glossary *Step*: "… is a **Story step** (Path segment and UI word: `build`)"; add "**New workflow** — the screen that creates a Run (FR-8)".
- **low** FR numbering is section-ordered, not numeric (FR-30 after FR-4; FR-31, FR-33 after FR-17; FR-29 after FR-24; FR-32 after FR-28) — deliberate and harmless, but a story writer scanning for FR-29..33 will read them as missing until found. *Fix:* one sentence in §0: "FR-29..FR-33 were added after numbering and sit in the section they belong to; ids are global and contiguous."

## Shape fit — strong

Capability-spec shape for a single-operator internal tool, with three UJs that carry a named protagonist and each end in an edge case — proportionate, not overhead. SMs are operational (completion rate, cold reload, recovery correctness) rather than user-facing, which fits. Brownfield references are to a method the Operator owns (`bmad-build-auto`, `stories.yaml` fields) and read as accurate against addendum §G's corrections. A few consequences are UX micro-specs that would live equally well in `EXPERIENCE-v1.md` (FR-21 "`COPIED`, ~1.2 s"; FR-24 "without animation"), but they are testable and harmless. No finding changes the verdict.
