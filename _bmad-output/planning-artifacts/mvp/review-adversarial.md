# Adversarial review — PRD: AI Orchestrator MVP (dev loop)

Reviewed: `prd.md`, `addendum.md`. Ground truth: `.claude/skills/bmad-build-auto/{SKILL.md, workflow.md, step-01-clarify-and-route.md, step-02-plan.md, step-03-implement.md, step-04-review.md, customize.toml}` and `.claude/skills/bmad-spec/assets/stories-schema.md`.

Verdict: the PRD is a good readout spec wrapped around a dispatcher contract that does not match the skill it dispatches. Five things the PRD takes for granted — the Answer path, subagents on every harness, "the Run commits", single-writer worktrees, and lock release on `needs-you` — are each contradicted by `bmad-build-auto` or by DBOS. Fix those before Day 1; the rest is ordinary tightening.

Severity: **critical 5 · high 8 · medium 17 · low 11** (41 findings).

---

## Critical

**[critical] The Answer mechanism has no counterpart in `bmad-build-auto` and the skill actively fights it** (§3 *Answer*, FR-18, Addendum D *Answer append*) — Nothing in the skill reads `## Human Answers`. FR-18 sets `status: draft` and re-dispatches. step-01 routes an existing `draft` file straight to step-02 (EARLY EXIT). step-02 item 1 captures the existing `<intent-contract>` *verbatim*; item 3 fills the spec template and "write[s] the result to `{spec_file}`" with that contract substituted back in. The template has no `## Human Answers` section, and the contract that produced `intent gap` is preserved unchanged; step-03 then treats `<intent-contract>` as read-only. Expected outcome: either the Answer is overwritten, or the agent re-blocks on the same gap. If the halt happened at step-01 (`no epic spec found`, `story id not found`, dirty tree) the file is a skeleton with no contract and the Answer is irrelevant anyway. The whole UJ-3 headline flow is unverified. *Fix:* (1) Add "Answer round-trip on a real intent gap" to the Day-1 verification queue (Addendum G) — it is not there. (2) Deliver the Answer through the channel the skill documents: append it to the dispatch prompt as additional planning context ("The story file contains `## Human Answers`; the intent-contract must be re-derived to incorporate it") *and* to the file. (3) Ship a `_bmad/custom/bmad-build-auto.toml` override (`activation_steps_append` or `persistent_facts`) stating that a `## Human Answers` section supersedes the preserved intent-contract on a `draft` resume. (4) State in FR-18 that a re-dispatch after Answer re-plans and re-implements from scratch (step-04 intent_gap *reverts code*), so the Story costs roughly 2x — the budget UI should say so.

**[critical] Subagents are mandatory; on any Harness without synchronous subagents every Story halts `blocked · no subagents`, and no human Answer can fix it** (FR-14, §4.5, §8 Q1, workflow.md *Subagents*) — workflow.md: "Using subagents when instructed is mandatory. If you cannot, HALT with status `blocked` and blocking condition `no subagents`." step-03's default `implementation_handoff` is a subagent; step-04 launches four reviewer subagents. For `claude` the tool allowlist (OQ6 lists only uv/git/package managers/test runners) must include the `Agent` tool, and `--bare` must not strip it. For `codex` OQ1 is open. For `local` (OpenCode) subagent capability is not even an open question. FR-16 will map `no subagents` to `needs-you` with a "Question" — there is no answer to that question; the operator's only real choice is Cancel. *Fix:* Day-1 verification: "each Harness completes one trivial story through step-04 with default handoff/review layers". Per-Harness fallback in FR-14: override `implementation_handoff` and `review_layers` in `_bmad/custom/bmad-build-auto.toml` to run inline (customize.toml explicitly permits "an override may run it any other way"). FR-16: classify non-answerable blocking conditions — `no subagents`, `no stories.yaml found`, `story id not found in stories.yaml`, `no epic spec found`, `unrecognized status in existing story file`, `finalization left repository dirty`, `review repair loop exceeded 5 iterations`, `context compilation verification failed`, `version-control metadata not writable` — as Step `error` with Retry/Skip/Cancel and *no* Answer box.

**[critical] The skill commits its own work; the PRD's commit Step is vestigial and its message never reaches git history** (FR-10 *commit*, §3 *Checkpoint* "after the Story's commit", FR-11, FR-23) — step-04 Finalize: write `status: done`, "Commit any reviewed-diff files that remain uncommitted", "Verify the version-controlled working copy is clean. Otherwise HALT with status `blocked` … `finalization left repository dirty`", "Do not push." So on the happy path the orchestrator's commit Step meets a clean tree and records `no changes` for *every* successful Story; `story {id}: {title}` is never a commit message; the done checkpoint's "after the Story's commit" refers to a commit the orchestrator did not make; the Steps table shows `no changes` next to every green verify. The §2.1 emotional job — "trust the green" — is lost on Run 1. Worse, the skill's own clean-tree check at Finalize halts `blocked` when the baseline gate left build artifacts, or an earlier intent-gap left its patch file in `{{.implementation_artifacts}}` (outside the Spec folder). *Fix:* Record `story_start_sha` on the Story step. Redefine the commit Step as a safety net: "commits leftovers (orchestrator edits to the Story file, untracked artifacts) with message `story {id}: {title} (orchestrator)`; records the range `story_start_sha..HEAD` as the Story's commits; records `no changes` only when HEAD did not move since the Story step started." Have the checkout/baseline Step verify a clean tree *after* the gate ran and fail loudly if the gate dirties the tree ("quality_gate_command must leave the tree clean" belongs on the Repository form).

**[critical] Orphaned harness after an orchestrator restart → two agents in one worktree** (FR-12) — "Killing the process during any Step and restarting resumes the Run at that Step; an interrupted Story step re-runs as a new attempt with a new Session id." A `claude -p` / `codex exec` child is not necessarily dead when the Python process dies (crash, `docker restart` of the orchestrator service, OOM of the parent); DBOS recovery knows nothing about OS children. The new attempt then runs concurrently with the orphan in the same worktree: two agents editing the same Story file and fighting over `.git/index.lock`. *Fix:* the Story step launches the child in its own process group and records PGID + start time on the `step_run`; attempt > 1 first kills the recorded PGID (TERM, then KILL), waits for `index.lock` to vanish, and only then dispatches. Add the testable consequence: "a re-attempt never starts while a previous attempt's process group is alive."

**[critical] FR-18/FR-19 actions race FR-21 terminal resumes in the same worktree, and the "status becomes `done`" poll fires before the agent has committed** (FR-18, FR-19, FR-21 third consequence, FR-24) — The operator can resume the session in a terminal (FR-21) *and* click *Resume with answer*; the orchestrator rewrites the Story file and launches a second harness into a worktree where the terminal agent is still running. In the other direction, FR-21 says "if the Story file's status changes to `done` … the Run resumes at verify on the next poll" — but step-04 writes `status: done` *and then* commits; the poll can fire between the two, so verify/commit race a live `git commit`. Frontmatter writes are not atomic either; a poll can read a truncated file. *Fix:* (1) Mutual exclusion: the Run detail disables Answer/Continue/Skip/Retry while a terminal resume is in progress — detect via an `.orchestrator/agent.lock` the harness wrapper writes, or an explicit "I am resuming in a terminal" toggle that sets a flag on the Run. (2) File-change resume requires `status: done` **and** a clean tree **and** no `.git/index.lock`, observed on two consecutive polls. (3) Unparseable frontmatter during polling is a transient, never an `error`.

## High

**[high] The verify-failure re-dispatch cannot fix anything** (FR-10 second consequence) — After `done`, the Story file is `done`. Re-dispatching folder+id routes `done` → step-04 *fresh review pass* (step-01 Intent check). step-02 never runs on that route, so "the failing output as context" — which the skill only consumes as "additional planning context to carry into step-02" — is discarded. step-04 re-runs the spec's own `## Verification` commands, not `quality_gate_command`. Net effect: the second attempt pays for a code review of the already-committed diff and `verify failed 2/2` follows deterministically. *Fix:* on verify failure the orchestrator appends a `## Verify Failure` section (command, exit code, tail of output) to the Story file and sets `status: in-progress` (routes to step-03: re-implement → verify → review, `baseline_revision` intact) before the re-dispatch; state that the re-dispatch prompt also says "the repository quality gate failed; see `## Verify Failure`". Put this route in the Day-1 verification queue.

**[high] Repository-lock release on `needs-you` contradicts the DBOS mechanism it is built on, and takes FR-25 down with it** (FR-13, FR-25, Addendum A *Durable engine*, Addendum D *Repository lock release*, §8 Q5) — A workflow parked on `recv` is still running as far as the queue is concerned; `partition_concurrency=1` will not admit another Run on that Repository. Addendum D's "the waiting Run leaving the queue partition while parked" is not a DBOS primitive: it means ending the workflow and enqueueing a continuation, which breaks FR-12's one-workflow resume, breaks FR-25's "the queue is read from the engine's queued workflows, not from a separate table" (a parked Run is a *running* workflow, so "position — · waiting for your answer" cannot come from the engine), and complicates the 30-day park. Q5 is asked in §8 yet the assumption is baked into a Day-1 design. *Fix:* decide Q5 before Day 1. The consistent cheap answer is HOLD: a parked Run keeps its Repository; the queue row reads `waiting: repository held by {run} (needs you)`. If release is truly wanted, the lock becomes the `repo_lock` row the architecture already lists and FR-25 drops the "engine only" claim.

**[high] Skip leaves the next Story dead on arrival** (FR-20 *Skip*, step-01 INSTRUCTIONS 3, UJ-3 edge case) — Skipping a `blocked` Story "leaves the file as is": the HALT protocol wrote it but only Finalize commits, so it is untracked — and after an intent gap there is also a patch file under `{{.implementation_artifacts}}`. The next Story's *first* dispatch reaches step-01 item 3: "require a clean working tree … HALT on a dirty tree" → `blocked` again. Skip after `verify failed 2/2` is worse: the breaking commits stay on the branch, no baseline is re-run, so every following verify fails and the cascade is silent until the operator reads outputs. *Fix:* Skip must either commit the Story's leftovers as `story {id}: skipped by operator` or reset to `story_start_sha` (operator picks; default reset, keep the Story file in the commit), then re-run the quality gate as a "re-baseline" verify before the next Story. State plainly that a Skip may leave the branch red.

**[high] Hidden dependency: the target Repository must carry BMAD and the skill, committed on the Working branch, in the right place for each Harness** (SKILL.md, Addendum B, FR-3, FR-8, FR-14) — SKILL.md executes `uv run {project-root}/_bmad/scripts/render_skill.py …` and halts *before the workflow loads* if it fails — so no Story file is written and FR-16 reports an unexplained `no story file`. Claude Code reads `.claude/skills` and, per Addendum B, `--bare` "skips skill auto-discovery except under `--add-dir`"; Codex and OpenCode read `.agents/skills`. FR-14 names the skill in the prompt but never adds `--add-dir`, and FR-8's pre-flight checks none of this. *Fix:* FR-8 pre-flight: `_bmad/scripts/render_skill.py`, `.claude/skills/bmad-build-auto` (claude) / `.agents/skills/bmad-build-auto` (codex, local) exist on the Working branch; `uv` present in the container. FR-14 `claude`: `--add-dir {worktree}` (or the explicit skill path) and an allowlist that includes `Agent` and `Bash(uv run:*)`.

**[high] A second Run on a branch with existing Story files re-reviews (and may modify) every `done` Story** (FR-10, FR-16, step-01 Intent check) — step-01 routes an existing `done` file to "a fresh review pass" with `review_loop_iteration` reset; `in-review` → review; `in-progress` → implement. The two-Runs-per-epic workaround (§6.2), a Run after cancel/failed, or simply re-running on a branch where three Stories are already done all dispatch Story 1 again and pay for reviews of finished work; patch findings will even change committed code. Nothing lets the operator skip already-done Stories. *Fix:* FR-8 pre-flight lists existing `stories/*.md` with statuses; FR-10 skips Stories whose file is `done` before dispatch (Step recorded `already done`, uncoloured) with an opt-in "re-review done Stories".

**[high] Worktrees and harness sessions are not declared to survive container replacement** (FR-12, NFR-7) — FR-12 promises resume across "container replacement" but `/work/...` is never named a volume, and checkout is a "completed Step [that] is not re-executed" — a resumed Story step lands in a worktree that no longer exists. Harness session dirs (FR-21) have the same problem. *Fix:* NFR-7 declares `/work` and the harness config/session directories as named volumes; the checkout Step is idempotent ("reuse the Worktree if present and on the right branch; recreate otherwise") and FR-12 says so as a testable consequence.

**[high] There is no Story-step (or shell-step) timeout anywhere** (FR-14, FR-26, NFR-1) — A hung harness — gateway stall, rate-limit backoff, or a subagent "await[ing] a completion notification" (the exact stall workflow.md warns about) — leaves the Run `running` indefinitely, holding the Repository lock and one of two global slots. FR-26's "Gateway unreachable fails its Step with `error`" is unobservable because the CLIs retry. *Fix:* `agent` and `shell` Steps carry `timeout` (defaults e.g. 90 min / 20 min); on expiry kill the process group, Step `error`, Run `needs-you` reason `timeout after {n} min`, Retry available.

**[high] Silent scope creep for a seven-day build** (§6.1, Addendum F) — §6.1 is one undifferentiated MUST list; Addendum F admits four things "slip first" but the PRD never marks them. Off the critical path of "story → verified commit": a CodeMirror editor + line-numbered validator + rendered diagram for a product shipping one Template (FR-5..7); daily Clone re-check cron (FR-4); login lockout (FR-1); Board LIST view (FR-22); "files changed since the Operator last opened this Run" (per-Run view timestamps) and "active Operator time" (client instrumentation nobody specifies) (FR-23); per-Project monthly spend (FR-28); full-surface fetch-error readout (FR-24); `gh` draft PR (FR-11); three Harnesses with unresolved Day-1 questions each; three needs-you verbs plus a terminal resume. *Fix:* add a MUST/SHOULD/COULD column. MUST: FR-1 (no lockout), 2, 3, 4 (on save only), 8, 9, 10, 11 (compare URL), 12, 13, 14 (`claude`), 15, 16, 17, 18, 19, 20, 22 (board only), 23 (no file-tree diff, no active time), 24, 26, 28. SHOULD: `codex`. COULD: `local`, FR-5/6/7 editor+diagram (YAML read-only), FR-21, FR-25 pagination, FR-27 span parenting.

## Medium

**[medium] "The Run stops for the Operator in exactly four cases" is false** (§4.6 vs FR-16, FR-17, plus the timeout above) — FR-16 alone adds `no story file`, `ambiguous story file`, `unexpected status: {status}`; each needs its own allowed actions and none has a Question. *Fix:* one table: reason → Run status → allowed actions (Answer / Continue / Retry / Skip / Cancel) → what the card shows.

**[medium] The Question shown will be the words `intent gap`, not the questions** (FR-16 second consequence, Addendum D *Story-file evaluation*, UJ-3) — The HALT protocol emits `Blocking condition: intent gap` on one line; the actual unanswered questions and evidence are free text elsewhere in `## Auto Run Result` (step-02 item 5, step-04 intent_gap branch). Addendum D says only the `Status:` and `Blocking condition:` lines are shown. *Fix:* render the entire `## Auto Run Result` section as markdown in the Question panel; the blocking-condition line is the card label only.

**[medium] `ambiguous story file` is unrecoverable and self-amplifying** (FR-16, workflow.md HALT item 1) — On ambiguity the skill writes a *third* file `{id}-ambiguous.md`. Retry finds three; Answer is meaningless; the operator needs a shell. *Fix:* FR-8 pre-flight checks that at most one file matches each id; FR-16 maps ambiguity to `error` listing the files with the instruction "delete extras in the Worktree, then Retry".

**[medium] "Liveness green" contradicts "never green" inside the same FR** (FR-16 first vs third consequence, §3 *Gate strength*) — *Fix:* replace "liveness green" with "liveness satisfied: Step `done`, rendered as the word `done`, uncoloured".

**[medium] Token/status mapping is incomplete and used inconsistently** (§3 *Status*, FR-22, UJ-3) — Tokens `QUE RUN BLK CHK ERR DON SKP CAN` include `CAN` (no Step status is `cancelled`) and omit `needs-you`/`failed`; UJ-3 shows `BLK` on a *Run* card. A budget halt has no token at all. *Fix:* two tables — Run status → token, Step status → token — and a rule: the card token is the needs-you *reason* token (BLK / CHK / ERR / BUD).

**[medium] "Every Harness process receives only: …" is unsatisfiable** (FR-14 fourth consequence, NFR-3) — The harness needs `PATH`, `HOME`, its config dir, `ANTHROPIC_BASE_URL`/`_AUTH_TOKEN`, `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA`, OTEL vars — and a git identity, because the *skill commits* (step-04 Finalize); without `user.name/email` the commit fails and surfaces as `finalization left repository dirty`. *Fix:* rewrite as a denylist ("never the GitHub token, never a direct provider key, never another Project's variables") and add "the checkout Step configures git identity in the Worktree".

**[medium] Baseline and verify assume dependencies are already installed** (FR-9, FR-10, FR-3 `package manager`, NFR-4) — A fresh worktree has no `node_modules` / `.venv`; `package manager` is stored but no Step uses it; NFR-4 allow-lists registries yet nothing installs. Baseline will fail on every fresh worktree unless the gate command self-installs. *Fix:* either state "`quality_gate_command` must be self-contained (install + check)" on the Repository form, or add an `install` shell Step to `dev-loop` v3 derived from `package manager`.

**[medium] Stale worktrees, shallow parents, and diverged remotes are unhandled** (FR-4, FR-9, FR-11) — A `failed` Run keeps its worktree (only Cancel removes it); the next Run on the same branch fails `git worktree add`. The FR-4 clone is *shallow*; used as the worktree parent it breaks step-04's diff since `baseline_revision` once history exceeds depth and can break push. A push after the operator pushed to the branch meanwhile is rejected (§5 forbids force) and the resulting status is undefined. *Fix:* the worktree parent is a full clone (the shallow one is the check only); checkout Step reuses or removes-and-recreates; push rejection → `needs-you` reason `push rejected (non-fast-forward)` with Cancel only, rebase out of scope.

**[medium] `failed` is terminal but Retry exists** (FR-9, FR-13, FR-20) — Baseline failure sets `failed` (terminal per FR-13); FR-20's "retry the current failed Step" has no Run status to live in. Nothing says what happens on day 31 of a park (NFR-1). *Fix:* baseline failure → `needs-you` reason `baseline failed` with Retry/Cancel; reserve `failed` for engine errors and park expiry, and say so.

**[medium] "Next poll" names two different polls and nobody owns the second one** (FR-18, FR-21, FR-24) — FR-24's poll is the browser; FR-21's is a server-side worktree watcher that must `send` to the DBOS topic. No FR defines that worker, its interval, or what it sends. FR-18's "within one poll interval" is 5 s or 30 s depending on unrelated Runs. *Fix:* FR-21 names a "worktree watcher" job (interval, condition, message); FR-18 replaces the poll language with "the Answer endpoint sends to the Run's topic synchronously; the Run has left `needs-you` when the endpoint returns".

**[medium] Cancel removes the Worktree while a process may still be running in it** (FR-20 *Cancel*, FR-13) — `git worktree remove --force` under a live harness or gate process; lock released while the process is alive. *Fix:* Cancel kills the process group, waits, removes the worktree, then releases the lock — in that order.

**[medium] The terminal resume command does not work from the operator's machine, and "remaining session lifetime" has no source** (FR-21, §5 last bullet) — Sessions live in the container's home; `claude --resume {id}` on the laptop finds nothing. Neither Claude Code nor Codex exposes a session TTL. *Fix:* the copyable string starts with `docker compose exec -u agent orchestrator …`; drop the lifetime or define your own retention on a volume.

**[medium] SM-2's "active time" has no defining FR** (FR-23 cost block, SM-2) — Printed and measured, never specified (focus? pointer? visibility?). *Fix:* FR-23: "active time = seconds the tab is visible with an input event in the last 60 s; posted every 30 s".

**[medium] A spec checkpoint offers read, but not reject** (FR-19) — The point of reviewing a plan is to correct it; the verbs are Continue/Skip/Cancel. The implicit alternative — edit the file in a terminal — reintroduces the same-worktree race. *Fix:* allow Answer at a spec checkpoint: append under `## Human Answers`, set `draft`, re-dispatch with "Halt after planning." (reuses FR-18 and inherits its critical finding).

**[medium] Addendum E cites FR ids from another numbering space without a prefix** (Addendum E, architecture-v1 line 70 "FR-10 stands") — `FR-24a, FR-28b, FR-29, FR-33..37, FR-38..42, FR-46, FR-50..52, F9` do not exist in this PRD; an engineer grepping will conclude the addendum is broken. (All ids cited *inside* prd.md — FR-1..28, UJ-1..3, NFR-1..7, SM-1..5/C1..3 — resolve.) *Fix:* prefix old ids as `PRD-0824/FR-n` everywhere, including architecture-v1.

**[medium] FR-2/FR-15 reinvent context injection the skill already provides, and risk hijacking intent detection** (FR-2, FR-15, customize.toml `persistent_facts`, step-01 Intent check) — A large Project context blob *prepended* to the folder+id instruction is exactly what step-01 must not mistake for "the invocation prompt as the intent"; it also bloats every dispatch. The skill loads `**/project-context.md` as persistent facts already. *Fix:* keep verbatim injection for the short context text; pass context files by path as "additional planning context: read …"; put standing project context in `project-context.md` on the branch.

**[medium] Cost has two sources of truth and the authoritative one lags** (FR-14 fifth consequence, FR-17, FR-28) — FR-14 records tokens/cost per Step (harness JSON); FR-17/28 sum Gateway spend logs; LiteLLM writes spend logs asynchronously, so a sum taken right after exit can miss the last calls and the budget halt fires one Story late. *Fix:* Gateway spend is authoritative; harness usage is display-only; the budget check re-reads until the log count is stable (≤ 10 s).

## Glossary and cross-reference audit

- **Run / Step / Story / Story file / Harness / Checkpoint** are used consistently in wording; the failures are semantic: *Checkpoint* ("after the Story's commit") and the commit Step assume the orchestrator commits (it does not, see the critical finding); *Story file* is "written by the agent" but FR-18 and FR-20 have the orchestrator writing or leaving it; *Status* tokens do not cover Run statuses (see medium finding).
- **"Story step"** (agent Step in the loop) vs **"verify Step" / "commit Step"** is consistent throughout §4.4–4.6.
- **Every FR id cited in `prd.md` exists** (FR-4, FR-11, FR-14, FR-15, FR-17, FR-18, FR-20, FR-21 cross-refs; §7 and §9 references; NFR/SM ids). Addendum E's old-PRD ids are the only dangling references.
- **Halt wording matches the skill** in one place: "Halt after planning." (FR-14) is the exact phrase step-02 checks; `ready-for-dev` halt status matches. Everything else about statuses (Answer, verify re-dispatch, done re-dispatch, dirty tree) does not.
