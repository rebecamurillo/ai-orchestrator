# AGENTS.md — ai-orchestrator (root)

Read this first, then the `AGENTS.md` of the component you are changing. This file is the constitution: it describes what the repository is, the rules no task may relax, and the commands that decide whether work is done. Rules here are checkable; if a rule cannot be checked, it belongs in a review, not here. `README.md` is the human-facing counterpart: setup, boot, and the operator walkthrough live there — do not duplicate them here.

## What this repository is

An orchestrator that runs BMAD dev-loop workflows against other repositories: a Run plans every step up front, executes them durably, dispatches stories to a coding-agent harness (claude, codex, opencode), verifies with the target repository's own commands, and stops for the operator only at declared checkpoints or when an agent is blocked.

Two deployables, one compose file:

| Component | Path | Stack | Talks to |
| --- | --- | --- | --- |
| web-client | `web-client/` | Astro 7 (SSR, Node adapter) + React 19 islands, TypeScript, pnpm | backend-api only, server side, with `Authorization: Bearer $ORCHESTRATOR_TOKEN` |
| backend-api | `backend-api/` | Python 3.14, FastAPI, DBOS (behind a port), SQLAlchemy 2, uv | PostgreSQL, git, harness CLIs, LiteLLM, Langfuse |

Shared at the root: `contracts/openapi.json` (generated by backend-api, consumed by web-client), `templates/*.yaml` (shipped workflow templates: `story`, `epic`, `initiative`, `repo-init`), `scripts/harness/*.sh` (per-harness install/configure/doctor), `.env.example` (the configuration contract), `docker-compose.yml`, `Makefile`.

The architecture is fixed by `_bmad-output/planning-artifacts/mvp/architecture/ARCHITECTURE-SPINE.md` (`AD-n` ids). When code and spine disagree, stop and say so; do not silently pick one.

## Architecture

**Code (AD-2).** backend-api is layered, direction enforced by `import-linter` in `make lint`:

```
domain  ◄─  application  ◄─  { api, infrastructure }  ◄─  main.py
```

- `domain/` — entities (Run, StepRun, Attempt, Project, Repository, …), status machines, and the ports (`Git`, `Workspace`, `ProcessRunner`, `Harness`, `Engine`, `Tracer`, repositories)
- `application/` — use cases (`create_run`, `plan_run`, `apply_step_result`, `signal_run`, preflight), one `StepExecutor` per step kind, template validate/plan, routing and budget rules — pure, no I/O
- `api/` — FastAPI routers under `/api/v1` behind one bearer dependency; Pydantic schemas are the contract; thin: parse → one use case → map
- `infrastructure/` — adapters: SQLAlchemy + Alembic (`db/`), DBOS (`dbos/`), git, workspace, process, `harness/<name>/`, LiteLLM gateway, Langfuse tracing, Fernet crypto, `settings.py`
- `main.py` — composition root; startup order: migrate → seed templates and harnesses → launch engine → schedule jobs → bind

web-client: Astro SSR pages, React islands, nanostores; the browser talks only to the same-origin proxy (`src/pages/api/[...path].ts`), which adds the bearer (AD-1). Layer detail and component-specific rules: `backend-api/AGENTS.md`, `web-client/AGENTS.md`.

**Infrastructure.** One postgres 18 database, two schemas: `public` (the application's, Alembic-migrated) and `dbos` (engine-managed — never write a migration for it). DBOS is the durable job runner (AD-6): only `infrastructure/dbos/` imports it, every side effect in the walker is a DBOS step with `retries_allowed=False`, the queue is partitioned per Repository (AD-12), and `DBOS_APPLICATION_VERSION` is pinned — bump it only when the walker's step sequence changes. Harness CLIs are installed in the backend image at the versions pinned in `.env.example` and run as the non-root user `agent`, in git worktrees under the `work` volume, with an env built from `HARNESS_ENV_CONTRACT` (`scripts/harness/_common.sh`) plus Project env vars — never the backend's own env. LiteLLM (spend, local models) and Langfuse (tracing) are optional host services: a blank base URL disables one, an unset variable refuses start-up.

## Hard rules (frozen — no task may change these to make a gate pass)

1. **Anchors are read-only.** Never edit `SPEC.md`, `stories.yaml`, `epics.yaml`, any `AGENTS.md`, or an existing test file (add new test files; never modify or delete existing ones). Four exceptions, all narrow. The first is a pending-gate registry: the story that lands a gate may remove that gate's entry from the list of not-yet-landed targets in an existing test, and only if the same commit adds a test asserting that the landed gate now runs. The second is a placeholder assertion: where a test names a later story as the thing that replaces what it asserts, exactly that story may revise that assertion, and only if the same commit adds coverage that strictly exceeds it. The third is a nondeterministic assertion: where an existing test asserts on the output of a third-party tool and that output is not deterministic across runs or releases, the assertion may be narrowed to the part that is, and only if the same commit adds a test that covers deterministically what the narrowed assertion stops covering. The fourth is an operator revision: when the Operator explicitly changes a product decision, the change they authorize may revise exactly the assertions that pinned the old behaviour, and only if the same commit asserts the new behaviour and the revised test names the decision and its date. This exception is the Operator's alone — it is never available to a dispatched agent: an agent whose story conflicts with an anchor still reports `blocked`, and the Operator granting the revision is what unblocks it. Nothing else in any of those files may change, and no exception available to an agent ever licenses deleting, skipping, or relaxing a failing test. Do not write the assertion that needs the second exception: a test covering a placeholder asserts that the route is served, not the placeholder's copy. The orchestrator checks this after every agent attempt and parks the Run on a hit (AD-17). A blocked story is reported as `blocked`, not worked around.
   **When a test fails after your change, classify before you touch anything.** (a) Your change broke the behaviour the test pins — fix the code; this is the default reading and needs no permission. (b) The test pins behaviour the Operator has explicitly decided to change — that is exception four: revise exactly the pinning assertions, assert the new behaviour in the same commit, name the decision and its date in the revised test, and quote the authorisation in the hand-back. A dispatched agent never classifies its own case as (b); it reports `blocked` naming the test and the conflict, and the Operator's ruling is what reclassifies it. (c) The test is wrong on its own terms — it asserts something the spine contradicts or a state it can never observe; that is a defect in the test, reported like any other defect, and revising it still needs the Operator's ruling. "The test is old", "the test is in my way", and "the suite is red anyway" are never category (b).
2. **Dependency direction** (AD-2): in backend-api, `domain` ← `application` ← {`api`, `infrastructure`} ← `main.py`. `domain/` and `application/` never import `fastapi`, `sqlalchemy`, `dbos`, `subprocess`, `os`, `shutil`, `httpx`, `langfuse`, `git`; all I/O goes through the `Git`, `Workspace`, `ProcessRunner` ports. `make lint` runs `import-linter`; a violation is a failed task.
3. **The contract is generated, never hand-written** (AD-3): API payload types in web-client come only from `pnpm gen:api`. Editing `src/api/schema.d.ts` by hand is forbidden.
4. **Status has two writers** (AD-8): `apply_step_result` for execution transitions (called by the walker inside the engine step) and `signal_run` for operator transitions. Executors, routers, adapters, and islands never write or derive a status.
5. **One credential** (AD-4, AD-5): `ORCHESTRATOR_TOKEN` is the only login; `GITHUB_TOKEN`, `LITELLM_API_KEY`, `LITELLM_SPEND_KEY` (backend only, never in a harness env), `LANGFUSE_*` are read in `infrastructure/settings.py` only; a harness process never receives `GITHUB_TOKEN`. Secrets never appear in code, tests, logs, or fixtures.
6. **TDD** (AD-18): a story's tests exist and fail before its implementation exists; a story is done only when every gate that has landed passes. `make lint` and `make test` always apply; `make e2e-api` and `make e2e-ui` apply from the story that lands them (1.2 and 1.3). A target that refuses with `not available until story <id>` is an unlanded gate, not a failure — once landed it is required from then on, and no story may return one to that state. Unit tests use the shared fakes in `tests/unit/fakes/`; do not create new doubles for a port that already has one. **No test, unit or e2e, may pin shipped template content** (step ids, ordering, counts, graph shapes, YAML text of `templates/*.yaml`): shipped templates are exemplars that evolve freely, and a test that would fail on a template edit is testing the wrong thing — cover template behaviour on fixture copies the test owns (Operator ruling, 2026-09-10; the 2026-09-15 e2e revision is what it costs to violate this).
7. **No silent retry.** A failed command is reported with its output. The only automatic retry in this system is the one a template declares (`retry: {max, prompt}`), and it is bounded.
8. **Configuration is the environment** (AD-20): a new setting is added to the typed settings module and to `.env.example` in the same change.
9. **Never stop the operator's running services without authorization** (Operator rule, 2026-09-18): `make down`, `docker stop`/`docker rm`/`docker compose down`, killing a listening process, or anything else that takes a running host, container, or dev stack offline is strictly forbidden without the Operator's explicit go-ahead in the current conversation. A port conflict is resolved by binding a different port; only when that is genuinely impossible, ask first — naming exactly what would go down and why — and wait for the answer. A standing instruction in a doc (such as this file's `make e2e-ui` note) is a procedure, not an authorization.

## Commands (the gates)

```bash
make up          # docker compose up: web-client, backend-api, postgres
make lint        # ruff · mypy · import-linter · eslint · prettier --check · tsc · env-contract check
make test        # backend unit (pytest) + web-client unit (vitest)
make e2e         # build the disposable aio-e2e stack, run e2e-api in it, destroy it
make e2e-api     # httpx scenarios + schemathesis against the running compose stack
make e2e-ui      # playwright against the built web-client (binds 4321; if held, ask the Operator before any `make down` — hard rule 9)
make durability  # kill the backend mid-Run, restart, prove the Run completes (own stack)
make openapi     # export contracts/openapi.json, then `pnpm gen:api` in web-client (fails on drift)
```

## Quality: how work is judged

TDD is hard rule 6; these are the enforced numbers behind it. `orchestrator.domain` and `orchestrator.application` hold 100 % branch coverage (`make test` fails under it); `web-client/src/lib/**` and `src/stores/**` hold 90 % lines; changed lines are 90 % covered (`make coverage`). Every source module has a test module naming it or `make lint` fails (test pairs). Unit tests need no Postgres and no network; e2e runs happen in the disposable `aio-e2e` stack so their leftovers never touch the dev stack. Raise a number by writing a test — a lowered threshold, an excluded file, or a `pragma: no cover` is itself the failure.

## Conventions that hold across both components

- Ids are UUIDv7; times are ISO 8601 UTC with `Z`; money is a decimal string in USD.
- Errors are RFC 9457 `application/problem+json`; lists are `{items, next_cursor}`.
- Status tokens are exactly: Run `queued running needs_you done failed cancelled`; Step `planned queued running done blocked checkpoint error skipped`; UI `QUE RUN BLK CHK DON ERR CAN SKP`. `skipped` and `unvalidated` are words on screen, never green.
- Conventional commits; the orchestrator's own commits read `story {id}: {title} (orchestrator)`.
- Product copy states facts and mechanisms; it never congratulates or apologises (PRD NFR-8).

## Trajectory capture

Every Story that reaches `done` with a green or skipped verify step writes one append-only `trajectory` row (AD-19). Do not add other data-collection paths.

## Guiding the operator through setup and first run

When the user asks how to boot, configure, or demo this system, walk them through `README.md` in its order rather than improvising: prerequisites → `make install` + `make doctor` → choose the environment mode (LiteLLM and Langfuse are each one variable in `.env`; blank disables, unset refuses start-up) → fill `.env` → optionally `make host-up` + `make host-env-sync` → launch in one of two modes: `make up` (containers, harness CLIs in the image — the default for client machines) or `make local` (postgres in compose, backend-api and web-client from source via `scripts/local.sh`, harness CLIs from the machine's own PATH; same ports, so never both at once) → verify → the operator flow (login, Project, Repository + clone check, `repo-init` if the target is new, then a Run from `/workflows/new` with a budget). Deployment to a client machine is `DEPLOY.md`; the host services are `host/README.md`.

Diagnostic order when something is red: `make doctor` before reading code (missing uv/Node reads as a test failure); every-write-answers-500 means the placeholder Fernet key; `localhost` failing where `127.0.0.1` works is the `::1` bind; readiness 401s mean no real provider key behind the Gateway; `Invalid model name … claude-opus-5` means Claude Code's default model is not in the Gateway's `model_list` — bind a model on the Run. Fix setup by naming the exact command, not by editing code, and never relax an anchor or a gate to get a machine green.
